# FlowEvo 失败驱动系统设计 v1：先证明机制，再生成修复算子

状态：设计建议，尚未实现或运行新增模型实验。依据为用户提供的AFlow机制设计、E3-S0原始事件审计及可信集/R-G-F试验。用户文稿中关于AFlow模块“已实现”的描述按提供材料引用，本轮未取得这些AFlow模块源码，未独立确认其实现状态。

建议将第一阶段的研究目标收敛为：**已核实的历史失败经验，能否形成跨题可复用的修复程序，并在相同模型、工具权限和预算下，比通用修复及纯文本经验获得额外收益。**

保留原设计的离线生成、开发选优、独立门控、证据绑定、拒绝和回退。修改重点是生成前的证据门槛、算子的执行对象，以及能够区分机制信息、工具使用和控制流程的对照。

## 1. 当前证据支持什么

| 已有事实 | 对设计的约束 |
|---|---|
| 800题、2,132候选中有1,644次旧失败信号 | 失败事件不是已验证的算法错误，不能直接聚类后生成算子 |
| 35题独立有限测试只覆盖155份候选 | 对其余候选保留未核实状态，不能把全部重评分当真值 |
| 两个确证缺陷分别是阶乘表容量与递归深度 | 都是实现缺陷，各只有一道来源题；尚无稳定跨题机制 |
| 两个缺陷都来自中间候选，原运行后来旧PASS | 不能把修好中间程序当成提升最终FlowEvo成功率 |
| 小规模试验G=4/4、F=4/4，只有两道任务 | 目前没有F超过通用修复的证据；重复调用不是独立题数 |
| 原历史库只复用旧PASS解，失败机制库为0 | 首先建设证据与发布时间链路，不能描述成已有失败经验持续进化 |
| 51次LCB反馈误译，17条实际进入修复 | 评价/反馈修复必须作为共同基础，不能全部归功于新算子 |
| 284个旧失败事件为空/语法错误产物 | 产物可靠性有工程改进空间，应与算法机制研究分开统计 |

上述数量来自E3-S0与trusted_rgf目录。30,172项检查通过证明档案和回放一致，不证明原评分器语义正确。

## 2. 建议修改原设计的地方

| 原设计环节 | 建议修改 | 原因 |
|---|---|---|
| 失败分类 | 分开记录评分可信性、程序缺陷、交付/基础设施故障 | “运行异常”可能是合法输入上的真实实现缺陷，不能全部排除 |
| 单题3次、错2次 | 必须是相同冻结条件下的独立生成/修复重复 | l1/l2a/l2b/l3/l4具有选择和反馈依赖，不是5次独立试验 |
| 最低错误率0.20 | 删除默认通用阈值，按完整采样框报告错误率与预算 | 只有失败样本不能估计发生率；低频严重错误也可能有价值 |
| 稳定失败→生成 | 增加跨题机制确认和剩余改进空间检查 | 一个可被普通修复轻易解决的Bug不必生成新算子 |
| 广义求解算子 | v1先实现插入l3/l4的修复算子 | 与历史轨迹、现有预算及可复核反事实直接对齐 |
| 两题、六观察晋级 | 只作为探索性工程筛选，不能叫泛化可信 | 同题重复会撑高观察数，且两题不足以支持范围性结论 |
| 多候选锦标赛 | 机制生成与无机制生成都给予相同K和筛选预算 | 否则可能只测到更多搜索和人工规格带来的收益 |
| 启发式路由分数 | v1采用适用/拒绝/未知三值规则，未知回退 | 当前机制数和校准样本不足，不需要学习精确概率 |
| experimental可检索 | 明确分成离线可见、shadow可见、正式可调用 | 可检索不应等价于可执行 |
| success即接受结果 | 保留原候选，公开验证通过才有资格被选择 | 执行成功不代表程序正确，不能覆盖已通过公开检查的候选 |
| 最终整体收益 | 分开检查点恢复、全流程净收益和真实在线积累 | 修复能力、路由能力、最终成功率是不同结论 |

## 3. 三层结构与两个门槛

```text
原始事件（全部保存）
  ├─ 评分/数据问题 → 评价账本 → 更正、失效传播
  ├─ 交付/基础设施问题 → 可靠性账本 → 通用工程修复
  └─ 合法输入上的程序缺陷 → 机制假设
                                  ↓
                       跨题证据门槛 M
                                  ↓
                       剩余改进空间门槛 H
                                  ↓
                    规格 → 候选 → 开发选优
                                  ↓
                    冻结 → 独立门控/回归
                                  ↓
                    shadow → admitted → active
```

这里不是排除工程改进，而是分别回答“系统更可靠了吗”和“失败经验产生了新的跨题修复能力吗”。递归上限、空代码检测等可以先作为工程基线中的通用措施；若因此消除了失败，就如实报告工程收益，不再包装成新算法发现。

**门槛M，建议作为小规模试验的操作规则：**

- 每个支持事件具有合法公开反例、独立参考计算、实际输出/异常、源码哈希、具体机制和局部反事实证据。
- 至少3道不同原题，且来自至少2个独立来源组，共享同一被违反的不变量。参数变体不增加独立原题数。
- 机制必须解释错误与非错误样本的差异，并通过近似反例检查。题面关键词相似不够。
- 不能靠“新规则仍WA”、模型自述或片段引用完成认证。

3题/2来源组只是进入实验的最低工程门槛，不是机制成立的统计证明。不足时停留在singleton/pilot，不能为凑机制数扩大语义范围。

**门槛H：**在冻结的相同修复检查点上，独立重复通用修复，检验该任务族是否仍经常失败。若通用修复已接近饱和，优先研究降成本或减少调用；若正确诊断提示也没有收益，进一步检查缺陷是否真被定位、模型是否具备执行修复的能力。不要立即扩大自动算子搜索。

检查点的一次修复失败率仅是该插入位置的指标；完整FlowEvo的最终失败率仍须由全流程独立实验测量。

## 4. 机制记录应增加的字段

```yaml
mechanism_id: factorial_capacity_v1
status: hypothesis | witness_verified | cross_task_supported | headroom_passed
failure_layer: evaluation | infrastructure | artifact | implementation | algorithm
violated_invariant: every reachable factorial index is allocated
causal_evidence:
  - source_event_id: task_x:l1
    code_sha256: ...
    legal_witness_id: ...
    oracle_id: ...
    actual_failure_id: ...
    minimal_patch_id: ...
    post_patch_validation_id: ...
support:
  independent_problem_ids: []
  provenance_group_ids: []
  sampling_frame_id: ...
  complete_observation_ids: []
  generic_repair_trials: []
boundaries:
  positive_applicability: ...
  near_miss_cases: []
  unknown_cases: []
time:
  observed_at: ...
  certified_at: ...
  published_at: ...
```

`observed_at`是看到失败信号的时刻；`certified_at`是合法反例和根因核验完成的时刻；`published_at`是机制/算子获准进入指定实验快照的时刻。回放只能读取当时已发布的记录。事后证明某个早期程序有缺陷，不能把机制知识倒填到早期时刻。

分别使用`mechanism_id`、`problem_id`和`provenance_group_id`。不同题可以共享机制；同一原题的重述、翻译、参数变体、近克隆属于同一来源组，不能跨开发/隐藏划分。更严格的跨题型或跨竞赛域迁移另做单独测试，不与普通跨题泛化混称。

## 5. v1算子：诊断并提出修复，不接管整题求解

推荐`MechanismRepairOperator`接口：

```text
输入：PublicTaskView + CandidateProgram + PublicFeedback
      + FrozenMechanismCard + RemainingBudget
输出：declined / proposed / error
      + 新程序或补丁 + 诊断证据 + 公开探针摘要 + 资源消耗
```

`PublicTaskView`只包含题面、公开样例、可公开约束及签名。**不包含隐藏input_output、标准解、私有失败样例、最终评分或未来阶段。** 沿用通用Retriever时也不能把`task.test`或`test_list`中的私有评测材料带入检索。

第一版固定骨架：

1. 确认前置条件：题意范围、AST特征、反馈类型、资源约束。
2. 选择有限个机制检查或独立公开探针；检查器本身须有可信依据。
3. 构造明确的违反不变量报告，而非只写“注意边界”。
4. 使用一个外层修复调用产生完整候选；算子内部不私自再调用模型。
5. 由控制器对源码、签名和公开检查进行验证，决定接受、拒绝或保留原候选。

v1可生成的内容为：有界AST分析、参数化检查规则、公开探针策略、结构化诊断模板与有限修复策略。任意整题Python求解器生成、无限探针搜索和多算子组合暂缓，避免把“算子”变成另一个预算更大的完整Agent。

两个已有缺陷用于接口与拒绝测试，不作为稳定跨题机制：

- **容量检查示例：**发现预计算表上界来自输入长度，但索引来源包含固定字母域。必须识别真实索引关系；不能见到`fact`就强制改成26。
- **深递归示例：**识别允许的深链与实际递归遍历关系。可以给出迭代化或资源设置建议；不能见到递归就抬高上限，不能用上限修改掩盖环或指数复杂度。

如果最后只有人工写出的这两条规则有效，应称为人工工程防护。只有生成程序在未见任务上实现了可测的跨题增量，才支持自动生成算子的结论。

## 6. 适用性、结果选择与预算

路由输入包括当前阶段、当前程序结构、公开反馈、机制前置条件、已验证范围和剩余资源。任务名、题目ID及标准答案不作为命中条件。

路由先检查证据/版本，再判断`applicable / inapplicable / unknown`。只在适用且预算充足时选择单个算子；多算子冲突、解析歧义或前置条件缺失时使用通用修复。v1不依据未经校准的0.70分数决定执行。

插入位置先固定在l3：

```text
l1 → l2a → l2b
             ↓ 未获公开接受
      [通用l3 或 专项l3]  ← 替换同一个调用槽
             ↓
      通用l4（如仍需修复且预算允许）
```

初始阶段三份候选/提示在对照条件间共享，以减少重复花费并确保同一检查点。此时估计的是“给定这个检查点，替换一个修复槽的效果”，不能直接外推到不同前缀的在线整体收益。全流程实验再独立运行。

控制器始终保留原程序和已有最好公开候选。专项返回`proposed`后不自动覆盖。空输出、语法错误、签名破坏、公开用例退化、超时均不能升级。公开检查有区分力不足时，按事先冻结的选择规则处理，不能查询最终隐藏评分挑赢家。

预算分两层：

- 检查点实验：一次修复槽、相同模型输出上限、相同输入/工具权限与公开探针预算；算子失败也消耗本槽，不额外免费补一次通用修复。
- 全流程实验：最多5个生成/修复槽；工具探针、路由耗时、失败调用和回退都计入总预算。执行专项前先预留回退资源，不足就不调用专项。

静态拒绝在未消耗模型槽时可以转通用修复；执行后回退须使用剩余预算，不能产生第6次免费调用。保留32768输出上限作为与历史配置的初始对齐值；不要为了预算方便随意降到易产生截断的设置。研究成本收益时另做预算曲线。

## 7. 评分与反馈必须先统一

保留两个参照，不能混用：

| 参照 | 用途 |
|---|---|
| 历史FlowEvo适配器及原反馈 | 回放历史、量化评分/反馈修订影响；不是主要因果对照 |
| 可信公开反馈下的FlowEvo-clean | 与新增机制、算子和路由比较的共同基线 |

FlowEvo-clean保持阶段骨架，修正错误码解释，明确公开与私有评分契约。生成/修复仅接收合法公开材料；最终隐藏评分在候选冻结后进行，不回传逐题错误以继续修复。

这与历史“全部基准测试参与反馈/停止”协议不同，必须新建实验版本。不能把协议改变产生的提升全部记到失败驱动方法名下。

成功解库也需要独立证据与来源隔离：旧PASS不能自动成为可信解；开发来源、候选接纳依据、有限测试覆盖写入库。主实验冻结相同成功解种子库，所有组共享，避免同时改变两种记忆机制。公开PASS只表示公开检查通过，不等价于隐藏正确。

## 8. 哪些对照能够支持什么结论

先定义四组；每组有同样的公开信息入口、模型和工具权限：

| 组 | 内容 | 主要用途 |
|---|---|---|
| G | 通用结构化修复 | 共同基线 |
| M | G + 冻结的跨题机制卡，仍按通用流程修复 | 估计纯文本经验价值 |
| O0 | 无专项失败机制输入生成的通用诊断/修复程序 | 控制程序工具、候选搜索和工程骨架 |
| O1 | 使用已核实机制与规格生成的修复程序 | 完整专项方法 |

O0/O1都生成K=3候选，设计集筛选预算、探针权限和修复次数相同。模型本来已有一般算法知识，不能把O0称为“完全没有机制知识”；它只是没有提供专项历史失败证据。

主要比较为O1−M和O1−O0；G是整体参照。只有O1−G改善，不能区分额外知识、工具执行、候选搜索和机制编译的贡献。若M与O1相当，优先使用更简单的经验卡，不为论文叙事强行保留生成程序。

进一步的同信息消融：把O1产生的合法诊断/探针结果原样给M，用同样一次修复调用。这样检查增益是否主要来自新诊断信息，而不是算子内部控制。该组必须另计探针和模型成本，不能把O1的诊断免费提供后宣称端到端同成本。

“人工专项算子”和使用答案选择的理想路由只作参考上界；不参与可部署系统的主要排名。

## 9. 可信晋级：范围性证据，不是一个综合分数

开发集按预先固定的顺序选优：接口/资源合格 → 专项净胜 → 回归损失 → 成本。综合Q分可用于排队，不能掩盖契约违规或回归。

隐藏门控只评估已冻结赢家，失败不能拿逐题门控反馈修复后再测同一集合。需要继续开发时，旧门控材料退役为已用数据，并准备新的独立来源组。

小规模gate通过只进入`experimental/shadow`。正式`admitted`需要：

- 多个未见来源组上的胜/负配对，按原题或来源组计算不确定性；
- 预先规定的系统回归/非劣界，以及足够样本支持该界；
- 净收益能覆盖Token、探针和回退成本；
- 契约/范围违例与失效依赖不能被分数抵消；
- 缺少统计证据时保持shadow，不把“没发现回归”写成“证明不会回归”。

生命周期建议为`candidate → development_frozen → gate_passed_experimental → shadow → admitted/active`；另有`rejected / suspended / retired`。只有正式策略允许的active版本进入默认执行。改代码、模型、评分、范围或关键依赖均需重新确认有效性。

## 10. 在FlowEvo的具体落点

**事实边界：**本次800题实际运行的是`benchmark.py`调用官方`code_math.runner.CodeSkillLibrary`的适配路径。官方仓库其他部分已有编译、注册表、负记忆和检索基础设施；不能因为本次路径未用到，就说整个FlowEvo都没有这些能力。

建议在服务器的可编辑FlowEvo源码工作副本上实现，不改写E3-S0和audit目录中的冻结代码。第一版新建适配入口`benchmark_failure_evo.py`，保留原`benchmark.py`作可复现参照。

| 拟新增/扩展模块 | 责任 |
|---|---|
| `failure_evo/contracts.py` | PublicTaskView、FeedbackView、MechanismCard、OperatorSpec、Budget与返回协议 |
| `failure_evo/event_store.py` | 事件、观测/认证/发布三时间与来源边 |
| `failure_evo/certifier.py` | 合法输入/独立oracle/反事实证据，未知不晋级 |
| `failure_evo/induction.py` | 机制假设与跨题支持，保留反证，不自动认证 |
| `failure_evo/operator_builder.py` | 固定骨架、多候选、有界生成/修复与制品摘要 |
| `failure_evo/admission.py` | 开发筛选、门控、证据版本有效性 |
| `failure_evo/router.py` | 三值适用判断、范围/版本/预算检查、单算子选择 |
| `failure_evo/controller.py` | l3槽替换、沙箱探针、候选保留、预算回退 |
| `failure_evo/evaluation.py` | 公共诊断与最终私有评分隔离、配对统计 |

上述文件是拟实施清单，不代表已存在或已完成。可复用官方schemas、trace_store、skill_registry、negative_memory_store及compiler/admission的设计，但先用适配层连接，避免直接让TACO/LCB走带不同测试可见性假设的旧接口。

## 11. 必须通过的系统验收

1. 空机制库、路由关闭时，预先给定响应的阶段控制和候选选择与FlowEvo-clean一致。
2. 更改隐藏答案、未来阶段、未来机制记录，不改变当前提示、检索与路由。
3. 任一制品/依赖/模型/评分版本不一致时，证据失效且不能默认执行。
4. 静态拒绝、超时、错误和剩余预算不足均得到可复核回退；总调用数不越界。
5. 原候选公开通过、新候选空/坏/退化时不覆盖；隐藏评分不参与在线选优。
6. 同原题变体、同源近克隆不能跨划分；各题重复不能增加独立支持题数。
7. 任一机制只有事后认证时，不能在历史时间提前进入记忆。
8. 生成、设计筛选、门控、失败请求、探针、路由、回退成本分项且总量一致。

## 12. 应如何描述研究贡献

当前可以说：已完成历史信息流和评分可信性审计，建立两个带反事实证据的实现失败案例。

下一步希望检验的是：**带合法反例和不变量证据的跨题失败记录，是否能被编译为有边界、可拒绝的修复程序，并在公平对照下提供超过纯文本经验的增益。**

若证据只支持反馈修正、产物可靠性或一般工具收益，就报告这些结果。稳定机制、自动生成的增量价值、选择性路由净收益分别需要独立实验支持。
