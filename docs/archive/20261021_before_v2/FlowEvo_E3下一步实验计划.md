# FlowEvo E3 下一步实验计划

状态：建议协议，未启动新增模型调用。**下一步先做E3-S1的系统与证据建设；满足机制证据门槛后，再做E3-S2的小规模改进空间试验。** 后续阶段全部带进入条件，不应一次启动整条流水线。

配套设计：《FlowEvo失败驱动系统设计v1》。本计划将原稿中的算子生成、可信晋级和路由分别验证，避免一次复杂实验难以解释收益来源。

## 1. 研究问题与预先约定的结论边界

| 问题 | 必须取得的证据 | 不能代替它的结果 |
|---|---|---|
| 是否存在稳定可迁移的失败机制 | 多原题、合法反例、共同不变量、独立重复 | 大量WA或同一道题多次报错 |
| 是否有必要生成新算子 | 通用修复后的剩余失败/成本空间 | 修好原本很容易修复的中间程序 |
| 生成程序是否超过经验提示 | O1对M、O0的配对增量 | 只超过没有经验和工具的基线 |
| 路由是否有净收益 | 混合任务中的恢复、误调用、回退和完整成本 | 理想路由下专项题提高 |
| 是否实现在线积累 | 认证/发布之后才被未来任务使用 | 把事后诊断回填到早期曲线 |

当前两种singleton缺陷和G=F的小试验仅作流程校验与饱和负对照，不据此启动大规模算子生成。

## 2. 数据角色与污染处理

原800题已进入历史分析体系，统一标记为`historical_exploratory`。其中即便某题还没逐题读过，也不把它包装成全新隐藏测试。

| 集合 | 来源和建议规模 | 可见性 |
|---|---|---|
| D_dis | 从800题中冻结48题审查队列，实际合格者组成发现集 | 可见 |
| D_des | 每个机制至少3道与发现来源组不同的开发题；可从历史队列合格余量补足 | 可见，允许候选修复 |
| D_gate | 最多2机制×12道未见专项题=24题 | 冻结候选后一次评估；开发者/生成器不可见 |
| D_reg | 24道新的非专项/近似反例/边界/冲突题 | 不反馈给候选继续修复 |
| D_test_pilot | 30道新的混合任务，用于完整系统试运行 | 系统冻结后一次评估；规模不足以作最终推广结论 |
| D_test_confirm | 后续另行确定规模的独立自然分布与专项测试 | 不因pilot结果好看而复用pilot题 |

隐藏/最终题来自未运行的候选来源池；可优先检查TACO官方测试集中未选原题和LCB release_v6未选题，但必须先核验授权可用性、去重与来源关系。不能保证这些池有足够独立合格题；不足时报告实际供给或更换来源，不用改写原题补齐独立样本数。

隐藏题由评价控制器/独立数据准备角色维护。开发端仅收到清单摘要、数量和来源组隔离证明，不读取题面/答案。这里的“独立”指信息与职责隔离，不是要求模型代理数量。

去重分三层：ID与规范化文本；来源/翻译/参数变体组；机制和结构上的近克隆审查。相同机制可以跨集合，但同源题组不能跨集合。生成的参数化反例可验证一个程序，不增加独立题目数。

## 3. E3-S1：系统机制与失败池建设，先不调用模型

### 3.1 冻结48题审查队列

| 抽样层 | 题数上限 | 目的 |
|---|---:|---|
| 重评分仍WA且未确证根因 | 24 | 寻找真实算法/实现缺陷 |
| 执行异常或TLE，尚未排除输入/框架问题 | 8 | 分清复杂度、实现资源与评价故障 |
| 新旧规则翻转 | 8，两个方向各4 | 复核评价敏感性，避免新错误进入发现集 |
| 已通过可信检查或相邻近似反例 | 8 | 建立机制边界与误触发对照 |

按dataset、difficulty、来源组冻结配额和候选次序；同题只占一个槽。使用`SHA256(seed|E3-S1|task_id)`在各层排序，不按“容易解释”补题。某层不足就按实际数量报告，或在审查前记录一次预定重分配，不能看到结果后换题。

每题检查所有已保存候选，最多48×5=240份；实际数以清单为准。已有2,132份程序优先离线复用，不重新生成。

每题证据包至少包含：题意约束、来源组、合法反例、参考计算、原程序与错误栈/输出、比较规则、根因假设、近似反例、最小反事实修改与修复后验证。参考计算优先小域穷举/数学不变量，或与主算法不同的独立实现；两份同源参考解不算独立佐证。

输入生成必须保持题面规定的行布局、值域和结构保证。非法输入仅用于独立的稳健性测试，不能用来认证功能失败。有限测试PASS仍只代表其覆盖范围。

### 3.2 第一版系统实现清单

在FlowEvo可编辑工作副本新增`failure_evo`适配层与`benchmark_failure_evo.py`，不修改冻结历史档案：

1. 公共任务投影、反馈契约与评价隔离。
2. 失败事件/认证/发布时间，机制与证据库。
3. 稳定机制门槛和剩余改进空间状态机。
4. 固定骨架修复算子接口、单算子路由和共享预算控制器。
5. 原候选保留、公开检查与回退选择。
6. 制品/模型/评分/依赖哈希失效传播。

先使用确定性人工夹具验证框架；夹具不能进入真实历史失败支持集。两个已知缺陷用于接口烟测和拒绝边界，不算新增机制。

### 3.3 验收与停止条件

- 所有当前提示/路由在修改隐藏答案、未来轨迹和未来机制库时保持不变。
- 关闭算子后可复现FlowEvo-clean控制逻辑；调用槽和总成本不越界。
- 每条机制来源能追溯到合法反例和实际程序，而非WA标签。
- **进入S2的最低条件：至少1个机制有≥3道独立原题、≥2个来源组支持。最多取2个。**
- 若未达到：输出“未建立跨题稳定机制”，保留工程防护收益并停止生成算子。可以另行扩大审查队列，但不能悄悄降低机制门槛。

产物：`review_manifest.json`、逐题证据包、`mechanisms_verified.json`、`public_view_schema.json`、框架验收日志、FlowEvo-clean版本清单。新增生成调用=0；静态解析、沙箱重执行与独立oracle运行均单独记录。

## 4. E3-S2：检查剩余改进空间，最多72次调用

### 4.1 样本与两种条件

最多12个真实功能失败检查点，按独立原题计数。每个机制保留至少3道来源题；可加入最多2个已知通用修复容易成功的singleton作为饱和负对照，但不让它们撑起稳定机制支持。

固定每个检查点的原程序、题面、公开反馈、公开反例和可用工具。三次重复都从相同初始状态开始，不继承前一次修复，也不把原FlowEvo各阶段当重复。

| 条件 | 输入 | 解释 |
|---|---|---|
| G | 通用修复指令和共同公开材料 | 主基线 |
| D* | G + 已审定的本题具体根因/不变量 | 诊断上界，非可部署方法 |

每条件独立重复3次、每次只修复一次：12×2×3=72次上限。D*有本题事后诊断，是有意增加信息的上界，不能宣称其收益来自跨题迁移。只使用合法公开生成的反例，不把私有门控反例发给G或D*。

请求模型/参数、最大32768输出Token、公共探针权限和工具资源相同。首先记录实际返回模型；若服务报告不同模型或关键配置漂移，停止对应比较并另开版本。历史实际返回deepseek-flash，不沿用deepseek-reasoner标签描述结果。

### 4.2 操作性决策规则

- 先报告各题G成功次数、D*成功次数、完整输出率和Token成本，再按机制汇总。
- 对一个机制，若至少2道不同来源题上G在3次中失败≥2次，认定存在值得继续研究的修复困难；这是pilot筛选，不是显著性结论。
- D*若在至少2道题上显示额外恢复，支持继续研究更有效的诊断供给；若没有，检查缺陷归因和修复执行能力，不自动增加候选数量。
- 如果G几乎全部成功，准确率方向暂停。只有在预先改成成本目标、统一精度条件后，才另做效率实验。
- 原系统后来已经成功的题，仅支持检查点恢复结论；不得计成全流程新增成功。

预算同时限制为**最多72次请求、300万新增Token**。每个六请求配对块开始前预留足够最坏预算；不足就不开始该块，完整报告未执行数量。Token包括输入、输出及已包含在输出中的思考Token，不重复加总。基础设施失败不自动重试，失败/未知消耗保留预算，防止遗漏成本。

产物：`headroom_protocol.json`、随机化块顺序、全部请求/响应、冻结最终评分、逐题配对结果。没有满足门槛的机制就到此结束，不进入S3。

## 5. E3-S3：小规模算子生成与开发筛选

只对S2仍有改进空间的最多2个机制执行。每机制至少3道独立开发原题，与发现来源组分离；不足就缩减机制数或停止。

### 5.1 控制“生成方法”而不只是控制执行模型

- O0：通用程序化诊断骨架，不提供专项历史失败卡。
- O1：相同骨架/工具API，提供已核实机制卡与规格。
- 每条件每机制K=3；每候选最多修复1次；两条件共享候选/修复/设计评分预算。
- 规格的算法知识也属于干预内容。若人工指定完整DP算法，必须记录，不能全部归为自动发现。
- 候选是修复控制程序，不在内部私增模型调用。外层统一负责一次修复请求。

在D_des上按题配对筛选每条件每机制一个赢家。设计阶段可见逐题反馈；候选一经冻结，代码、模板、范围、工具策略和依赖哈希都锁定。

### 5.2 上限计算

当2机制、每机制3道开发题、每题2次独立修复重复时：

- 生成/有限修复：2机制×2条件×3候选×最多2次=24次请求。
- 候选设计评估：2×2×3×3×2=72次修复请求。
- G与M开发参照：2组×6题×2次=24次请求。
- 合计最多120次、建议Token硬上限600万。未耗用修复预算不转成额外候选。

工程筛选优先检查接口、非法访问、资源、适用性和输出；没有合格赢家的机制不发布。静态检查加沙箱，不用静态检查替代隔离。

产物：`operator_specs/`、候选及设计轨迹、O0/O1各自开发赢家、不可变制品清单。隐藏门控失败后不允许用同一集合再选第二名。

## 6. E3-S4：独立门控，区分程序、经验与机制生成

建议上限48道新原题：24专项（最多2机制各12）及24非专项/边界题。回归侧预分普通、近似反例、边界和冲突；某类没有真实供给就按实际报告，不能用同源变体凑独立题数。

四组G、M、O0、O1共享同一初始程序和公共材料、同样的工具入口、探针上限与一次修复槽。M只带冻结跨题经验；不能混入本题D*诊断。评估O1−M、O1−O0为预先指定主要比较，O1−G为系统参照。

### 6.1 新题检查点的成本与选择偏差

新题没有现成历史错误程序。为每题先独立生成1份共同初始程序，最多48次，纳入总成本；**不反复生成直到找到错误**。

初始程序有的本来正确，全部保留。预先按机制适用范围选题，不根据隐藏失败结果筛掉容易题。一次修复的强制检查点评估用于测恢复、误改和拒绝能力，与真实l3路由分开解释；完整FlowEvo仍在S5评价。

四组×48题×2次修复重复=384次；加48次初始化，**最多432次，建议Token上限2,000万**。部分拒绝路径实际少用调用，但不能把省下的调用转成多次试错。预算只是上限提案，需在启动该阶段前按输入大小验证最坏预留；不足时在揭示隐藏结果前缩减预注册样本，不能评到一半挑选已完成的好结果。

### 6.2 指标和晋级

报告W、L、T、不同获胜原题数、按原题/来源组聚合的净增益与不确定性；同题两次重复先合成题级结果。多机制/主要比较数事先冻结，不能选表现最好的比较作唯一报告。

同时记录：初始正确→修复错误、拒绝、执行错误、探针实际消耗、Token、完整输出率、范围违规和系统回退成本。参考程序与评分器的契约审查独立于候选表现，无法确证评分的题单列为未知，报告其剔除原因和敏感性分析。

- 有契约/范围泄露或隐藏材料进入生成：该版本无效。
- 只有G落后，但O1不优于M/O0：不支持生成专项算子的增量价值。
- 小规模结果有正向趋势但区间跨零：最多作为experimental/shadow，不称为可信active。
- 达到预先规定且样本支持的净增益/回归要求，才进入全流程试运行。具体非劣界应在门控前按可接受损失冻结，不能沿用“回归≤10%”作为默认可信保证。

## 7. E3-S5：完整FlowEvo接入与路由试运行

先做30道新混合任务的工程pilot，三个系统组：

1. FlowEvo-clean。
2. FlowEvo-clean + 规则路由的经验卡M。
3. FlowEvo-clean + 有范围/证据/预算约束的O1路由。

全部保持最多5个模型槽，v1只替换l3，其他流程一致。最多30×3×5=450次请求，建议Token上限2,000万；只做一次完整运行/题，重复性由后续确认试验补充。共享缓存若用来节省共同前缀，须同时报告实际付费调用和各系统完整逻辑成本，不能把共享前缀成本只记给基线。

30题为预先配比的混合试运行，不是自然分布总体成功率估计。报告专项与非专项结果，明确采样富集情况。自然分布的最终确认集另行按完整采样框随机抽样，不能把富集数据加权成未知总体。

主要终点：完整系统最终正确率、原题级净胜、正确时间内完成率，以及总Token/时延。辅助终点：专项覆盖率、误调用、拒绝、冲突、回退、公开正确候选退化、路由选择原因。隐藏最终结果不参与中途修复、候选选择或库更新。

对照组在同样的公开反馈协议下运行。旧原版历史结果仅列旁表，不把历史隐藏反馈协议下的488/800与新协议结果直接作机制因果比较。

若三组都没有增益，先分解“机制无收益、适用性识别差、误调用抵消、预算/截断抵消”。不直接扩大为多算子组合或增加免费回退。

## 8. 真正在线积累另做预注册扩展

只有S4/S5支持跨题增量后，才做在线库更新：

```text
学习块 t：保存失败 → 独立审查 → 机制认证 → 开发/新门控 → 发布快照 t+1
评估块 t+1：只使用发布快照，任务结束后不把其隐藏反馈用于本块继续更新
```

学习流与最终评估流分离，最多更新次数和每轮新的门控材料预先固定。画出失败信号、认证机制、发布算子、未来任务实际命中和累积净收益五条曲线，横轴使用实际发生/认证/发布时间。审查、生成、门控成本及延迟全部计入；不能预载800题的事后机制后称为在线冷启动。

这一步还可以研究“多条稳定失败是否比随机失败事件更有价值”，使用相同事件数量、来源组数、模型和预算的随机/不稳定失败对照，而不是直接将所有1,644次信号混作机制来源。

## 9. 阶段总表与优先顺序

| 阶段 | 当前是否具备进入条件 | 新增模型请求上限提案 | Token上限提案 | 决策 |
|---|---|---:|---:|---|
| S1：证据池与系统MVP | 是 | 0 | 0 | 立即优先 |
| S2：检查点改进空间 | 尚缺跨题机制证据 | 72 | 300万 | S1达标再启动 |
| S3：生成与开发筛选 | 尚不具备 | 120 | 600万 | 仅对有空间机制 |
| S4：隐藏门控 | 尚不具备 | 432 | 2,000万 | 仅冻结赢家 |
| S5：完整系统pilot | 尚不具备 | 450 | 2,000万 | 仅有独立增益证据后 |

这些是分阶段建议，本轮尚未启动新增模型实验，也不要求用满配额。**不应现在承诺一口气用完1,074次请求和4,900万Token；很可能在S1或S2就应停止或转向。** 每阶段实际样本不足、预算不足或评分未知都如实报告，不自动补题或降低门槛。

推荐的第一份实施提交应只包含：公共/私有数据隔离、失败证据状态机、修复槽接口、共享预算与回退、S1冻结抽样和系统验收。待机制池与改进空间过关，再提交生成器和锦标赛；路由学习与在线动态更新最后实现。
