**你的原设计值得保留，不需要推倒重来。但要从“等到稳定失败足够多，再离线生成专项求解器”，改成“在线积累可信失败证据，按预算生成候选，在后续任务中验证和使用”。**

我建议保留你原来的三个核心环节：**算子生成、可信晋级、选择性路由**。这三个环节已经覆盖了研究的主要问题；需要修改的是它们之间的触发条件、数据时序，以及在 FlowEvo 中的介入位置。你的原文对“可信不是全域正确保证”、版本绑定、独立门控和回退成本的规定，也应继续保留。粘贴的文本 (1)粘贴的文本 (1)

# 一、原方案最大的矛盾：把“允许开始学习”和“允许正式部署”用了相近的高门槛

你的原设计要求：每题发现运行3次，至少错误2次，再积累至少3道不同稳定失败题，才能进入机制归纳和生成流程。这个规则有助于避免针对偶发错误过拟合，但对现在的稀疏失败场景，会导致系统很难启动。粘贴的文本 (1)

而且，它还把两件不同的事情捆在了一起：

> **有没有足够证据，值得花一点预算生成候选？**

以及：

> **有没有足够证据，可以让这个候选影响后续真实任务？**

我建议将两道门槛分开：

| 决策 | 建议要求 | 允许做什么 |
|---|---|---|
| **启动候选生成** | 一条可信失败、明确的干预目标、有办法低成本验证 | 生成候选，进入影子验证 |
| **允许受控试用** | 接口、安全、来源案例和独立正反测试通过 | 只在预注册试验分支调用 |
| **允许正式复用** | 在后续独立对象上获得可靠性或成本收益，回归风险受控 | 纳入有明确范围的在线路由 |

**一条失败可以启动学习，但不能直接授权部署。**

这样，你不再需要等同一个错误先出现很多次，也没有放弃验证要求。

这里的“可信失败”同样不限定为高级算法错误。输出不完整、数组容量不足、递归深度超限，都可以进入对应的候选生成流程。只是：

**确认“失败发生了”，不等于确认“失败原因是什么”，更不等于确认“生成的算子有用”。**

这三种证据要分别保存。

# 二、结合现有实验，应该修改原设计的六个地方

## 1. 将“稳定失败题”改为“可信失败事件＋后续复用证据”

E3-S0已经重建了2,132个候选事件，其中284次是可以直接确认的空代码或语法不完整产物，涉及130道题。另一方面，两个已验证实现缺陷都来自中间候选，原运行后来得到过旧评测器的PASS。E3-S0报告E3-S0报告

因此，**不应再用“题目最终失败”筛掉学习材料**。

建议将事件记录扩展为：

```text
任务和题目家族
当前工作流阶段
当前代码及父版本哈希
实际观察到的失败
输入合法性和验证器可信状态
原因解释的证据等级
后续修复证据
观察时间、验证完成时间、最早可用时间
获取与验证成本
```

特别是三个时间应分开：

**错误发生时刻、错误被验证的时刻、相关知识允许进入系统的时刻。**

这能直接解决E3-S0右图的问题：事后认证的两种缺陷不能倒填到历史早期的经验库中；但可以作为现在的开发材料，或者在明确声明的“预载历史经验”实验中使用。E3-S0报告

### 一个重要调整

不要把“产物失败”和“合法输入上的功能失败”理解为高低贵贱不同的研究材料。

它们只是支持的干预不同：

| 已确认的事实 | 可以尝试生成的算子 |
|---|---|
| 输出耗尽，未形成完整代码 | 代码交付恢复、生成预算分配、候选回退 |
| 合法输入导致数组越界 | 有范围约束的容量分析与局部修复 |
| 合法深链导致递归异常 | 深度风险处理、受限资源调整或迭代化修复 |
| 旧评分器报告WA，但输入和答案未核验 | 暂存和分诊，不能直接生成已确证的算法修复规则 |

**真正应该限制的是证据能支持什么动作，而不是错误是否足够“高级”。**

## 2. 将“任务专项求解器”扩展为“工作流阶段算子”

你原文对算子的定义其实已经足够宽：允许提示模板、模型调用、确定性算法和参数化工具组合。但后面的路由与示例，主要围绕“输入一道题，选择一个专项求解器”展开。粘贴的文本 (1)粘贴的文本 (1)

对现在的FlowEvo，更合适的首批算子不一定是完整解题器，而是：

**在特定执行状态下，完成一个可复用恢复步骤。**

例如：

| 类型 | 输入 | 输出 |
|---|---|---|
| 工作流恢复算子 | 题面、截断响应、已有候选、剩余预算 | 恢复动作、新候选或拒绝 |
| 程序修复算子 | 当前源码、公开失败证据、任务约束 | 有范围限制的修改及验证结果 |
| 完整求解算子 | 可解析的问题族实例 | 计算结果或完整程序 |

我建议**本轮先实现前两种，暂不强求完整求解器**。

不是完整求解器不能研究，而是你现在最充分的证据来自产物交付和局部实现问题；让一个这样的证据直接驱动完整求解器生成，会无谓扩大生成和验证空间。

同时，需要正视原文指出的实现现状：主闭环目前标识为 `fixed_skeleton_prompt_only_v1`，另有代码生成模块，不等于已经打通统一程序合成。粘贴的文本 (1)

因此，下一轮必须记录清楚：

> 生成器到底生成了新的可执行控制逻辑、局部代码变换，还是只生成了一段更长的提示？

三者都可以研究，但不能混称为同一种“算子生成”。

## 3. 将“离线生成、在线只调用”改为“题间编译、下一题发布”

原设计规定离线阶段负责发现、生成和验证，在线只使用已经发布的算子。这有安全性优势，但还没有实现你期待的持续积累过程。粘贴的文本 (1)

建议保留隔离原则，但改成两条循环：

```text
任务执行循环：
FlowEvo正常执行
→ 观察失败
→ 已发布算子按条件介入
→ 完成本题
→ 保存本题可用经验

题间学习循环：
累计失败证据
→ 有界生成候选
→ 设计集筛选
→ 独立门控与回归
→ 发布新版本
→ 下一题或下一批任务开始使用
```

**新代码不能一生成就进入当前任务的正式执行路径。**

第一版可以采用简单的批次屏障：每20道任务检查一次编译队列；第一条高可信见证也可以在题末触发首次编译。具体间隔是实验参数，不是理论最优值。

这同时实现了：

- 持续积累；
- 动态产生算子；
- 新代码经过验证；
- 可追踪“什么时候开始产生收益”。

编译器和求解器可以使用同一个模型顺序执行，不需要另起多Agent系统。编译、验证及等待时间都应记账，不能当作免费后台工作。

## 4. 修改晋级标准：允许“同样做对，但更便宜”

你的原晋级门槛要求至少两道不同获胜题、至少两次净胜。如果两种方法最终都做对，但算子省掉了两轮修复，就无法通过这个正确率导向的门槛。粘贴的文本 (1)

这与你目前的研究目标不完全一致。

建议设置两条晋级路线：

**可靠性路线：** 相同预算下，增加正确完成或减少错误传播。

**效率路线：** 在预先设定的可靠性约束下，减少修复调用、Token或延迟。

例如：

```text
原FlowEvo：
生成失败 → 重新生成 → 再失败 → 修复成功

加入算子：
生成失败 → 受限局部修复成功
```

最终成功率可以相同，但后者仍可能值得复用。

当然，**不能因为在线少用了Token，就忽略算子的构建和验证成本**。建议以同一计量口径计算：

\[
\mathrm{NetSaving}(N)
=
\sum_{i=1}^{N}
\left(C_{\mathrm{base},i}-C_{\mathrm{new},i}\right)
-
C_{\mathrm{induction}}
-
C_{\mathrm{gate}}
-
C_{\mathrm{learning\ audit}}.
\]

这里的新系统在线成本应包含检测、路由、执行、原生续跑和回退。正确率与净节省并列报告，不能让“便宜地失败”被当作效率提升。

原文关于回退可能叠加调用成本的提醒，应完整保留。粘贴的文本 (1)

## 5. 修改生命周期：Shadow不能进入实际路由

原设计说明，当前实现会把 `experimental`、`admitted`、`active` 都纳入可检索状态，虽然还有证据门控，但状态与执行权限之间仍不够清晰。粘贴的文本 (1)

建议明确为：

```text
draft → shadow → experimental → active
                  ↓               ↓
               rejected       suspended / retired
```

关键不是多几个名称，而是权限：

- **shadow**：只做离线或影子评价，不能影响模型提示或行动。
- **experimental**：只能进入预注册的受控试验分支。
- **active**：只能在证据绑定的范围内用于正常任务。

尤其要注意：把Shadow算子的内容“仅作为提示”发给模型，也已经改变了行为，不能再叫无干预影子评估。

## 6. 路由和回退要接到FlowEvo的实际执行阶段

原路由是：

\[
g(x)=\text{选择某个算子，或使用基线}.
\]

建议改成：

\[
r(x,\text{阶段},\text{当前代码},\text{反馈},\text{剩余预算},\text{库版本}).
\]

因为同一道题在“还没生成代码”和“已有代码但刚刚递归失败”时，适合调用的算子不同。

首版只需要两个介入位置：

```text
before_native_retry：原生重新生成或修复之前
before_final_return：最终返回程序之前
```

每个位置最多尝试一个算子，不做多算子串联、不做无限补救。

**拒绝或失败后，恢复同一检查点的原FlowEvo续跑，而不是另外启动通用两阶段求解器。** 原文当前回退是“通用分析→通用求解”，迁移到FlowEvo后需要替换，否则会混入一个新的求解基线。粘贴的文本 (1)

# 三、建议的算子接口：返回“干预结果”，而不是直接宣称答案正确

可以保留你原来的五元组 \(o=(S,P,V,E,L)\)，扩展规格中的上下文字段：

```yaml
operator_kind: workflow_recovery | code_repair | task_solver | prompt_policy
hook: before_native_retry

inputs:
  task_public: ...
  candidate_code: ...
  public_feedback: ...
  generation_metadata: ...
  candidate_ledger: ...
  remaining_budget: ...

preconditions: [...]
allowed_actions: [...]
decline_conditions: [...]
postchecks: [...]
fallback: resume_native_continuation
```

返回结果建议区分：

```yaml
status: applied | declined | error
candidate_code: optional
selected_candidate_id: optional
validation_status: not_checked | structural_pass | public_tests_pass | failed
actual_cost: ...
evidence_ids: [...]
```

这里有三个约束。

**第一，`applied`不等于正确。** 算子可能成功生成了代码，但代码依然有功能错误。

**第二，算子不能给自己增加权限。** 不能改评分器、扩大总预算、关闭沙箱或自行提升为Active。需要调整运行参数时，只能向宿主申请预先允许的动作。

**第三，候选更新应可撤销。** 新程序验证失败时，应保留之前的候选，并在剩余预算内恢复原流程。不能利用隐藏评分挑选“历史最优程序”。

# 四、在FlowEvo上实现时，不要再同时更换整套运行栈

这里我建议修正此前“优先迁移到完整执行路径”的推进方式。

**现在应先固定你已经运行800题的实际FlowEvo入口，在它上面添加失败学习插件，而不是一边换入口、一边改检索、一边新增算子。**

E3-S0恢复的实际路径是：前三个阶段重新生成，后两个阶段才接收上一候选及反馈；跨任务引用的是前序成功解。E3-S0报告

我本次核对的官方代码也确实区分两种路径：`src/code_math/runner.py`中存在简化成功例检索和分级重试；`src/eval/runner.py`另连接执行器、技能编译和多种存储。不能只根据仓库名称，把两种运行都称作同一套完整系统。

推荐做一个最小扩展：

| 模块 | 功能 | 复用你原设计的哪部分 |
|---|---|---|
| 失败事件存储 | 时序、可信度、源码和证据引用 | E3-S0事件文件与机制档案 |
| 编译调度器 | 何时启动、去重、冷却、预算限制 | 修改稳定失败门槛 |
| 失败算子编译器 | 规格、真实制品生成、有限修订 | 机制归纳和generation模块 |
| 晋级与注册 | 门控、回归、版本、撤销 | tournament与operator library |
| 阶段路由器 | 固定Hook、单算子、拒绝、原生续跑 | contextual operator router |

这些是建议模块，不是已经核验的服务器文件。

原成功Skill机制保持共同基线配置；新失败算子使用独立命名空间。FlowEvo本身已经以成功轨迹编译、复用和治理为主要思路，因此新研究应证明失败通道提供了什么额外价值，而不是把原有成功经验能力重新命名。[GitHub](https://github.com/DEFENSE-SEU/FlowEvo)

另外，**所有对照组必须共享已修复的评分器、错误码、I/O、安全执行和费用记录**。不能让基线继续使用错误比较器，再把评分修复收益计到新方法头上。

# 五、下一步实验：不要再统计一遍失败，开始真正生成和试用候选

我建议下一轮分为四个阶段。前两阶段是当前重点，后两阶段在前面出现可信证据后再执行。

## 阶段A：E3-S1.1——最小学习器实现

**目标：把事件积累、候选生成、晋级和阶段路由接起来。**

直接复用现有E3-S0事件和可信评分组件，不再重新审计800题。

本阶段新增模型API为0，主要检查：

**插件关闭时，原FlowEvo行为是否保持；Shadow是否不影响模型；新版本是否只在题间发布；算子拒绝是否回到原生续跑；隐藏信息、预算和权限是否受到控制。**

这里可以用固定历史响应和工程探针做回归。不需要真实模型重新生成相同答案，也不要求出现足够的算法错误。

这一步的交付应是实现差异与运行证据，而不是又一份失败类别报告。

## 阶段B：E3-S1.2——最多两个算子族，真实生成候选

我建议首批目标这样确定。

### 主目标：产物不完整之后的恢复选择

理由是它有284次直接产物失败事件作为开发材料，不依赖仍有争议的WA判分。E3-S0报告

但**不要把“检测语法错误”本身当成失败学习创新**。基础语法解析和结束原因读取应由所有组共享。

真正让生成器学习的是：

> 在什么阶段、什么已有候选状态、什么剩余预算下，采取何种有界恢复动作更划算？

候选可以选择代码优先重新生成、利用最近完整候选、局部恢复或拒绝。并非这些动作本身都是创新，增量要靠与Generic对照验证。

### 第二目标：数组容量与可达索引范围不一致

可以用已有容量缺陷作为开发见证，生成有结构适用范围的程序修复候选。

但不要把旧补丁直接做成“所有题都将 \(n\) 改成26”的算子。生成器需要给出适用条件、允许的修改和验证方法。

递归深度机制可以保留为备选，不必为了显得完整同时开发三种。

### 候选预算

建议最多两个算子族，每族：

- 3个初始候选；
- 每个候选最多1次设计集修订；
- 规格归纳最多1次模型调用。

因此，**生成、修订和规格归纳合计最多14次模型请求**。门控评价中使用的模型调用另计，提前冻结预算。

这一步必须实际调用生成器并保存制品来源。不能研究者先写好专用恢复规则，再声称系统从失败中生成了它。

**只生成候选，不要求必须晋级。** 没有足够独立验证材料，就保持Shadow；但不因为来源错误只出现一次，就连候选都不允许产生。

## 阶段C：E3-S2——24个真实检查点，比较是否有增量价值

从算子来源与设计材料之外，按预先固定的顺序选择最多24个真实历史检查点：

| 检查点类型 | 建议数量 | 用途 |
|---|---:|---|
| 目标失败 | 12 | 检查恢复作用 |
| 没有目标错误的完整候选 | 6 | 检查误干预 |
| 相似症状但不同原因，或超出适用范围 | 6 | 检查拒绝边界 |

不足就按实际数量报告，不人工注入错误来填满主样本。

这些属于**开发性挑战集**，不是自然失败率样本，也不是完全独立的新方法最终测试集。

### 四个条件

| 条件 | 内容 | 要排除的替代解释 |
|---|---|---|
| **B** | 共同工程修复后的FlowEvo原生续跑 | 基础参照 |
| **G** | B＋基于公共规格的廉价通用检查与恢复 | 是否普通工程规则已经足够 |
| **M** | B＋与F相同失败证据的文本知识卡 | 是否只需要语言经验，无需可执行算子 |
| **F** | B＋生成并经门控的可执行Operator | 你的候选方法 |

我认为**M组是原设计最需要补上的对照**。

否则，即使F优于原FlowEvo，也无法区分：

> 是失败知识有用，还是将知识编译成可执行操作更有用？

在这个条件性实验中，可以让M和F使用相同的证据、适用范围及触发点，只改变知识的使用方式。

G组也要足够强。例如对产物失败，它至少应该包含合理语法检查、代码优先恢复和基于公开信息的候选保留策略。不能让G只是“请再想一想”。

### 如何运行

每个检查点的四组从相同的任务、代码、公开反馈、剩余预算和成功Skill库快照开始。

24个检查点×4组，最多96个分支；它们不是96道独立任务。

**F一旦改变程序或Prompt，后续就必须真实运行，不能继续接上原历史轨迹。**

这一步回答的是：

> 给定相同失败状态，已生成算子能否比Generic和同证据文本记忆更可靠或更便宜？

不是回答自然环境中这种失败有多常见。

## 阶段D：E3-S3——60题真实顺序流

只有阶段C出现可复核的增量价值，才进入这个阶段。

建议使用60道未参与设计的新题，按元数据和可信准入选取，而不是先跑模型再挑错误题。可以设3个批次，每批20题。

运行过程：

```text
第1批：失败库为空，观察并积累经验
批末：候选生成、独立门控、发布

第2批：使用已发布算子，同时继续积累
批末：更新候选与发布状态

第3批：继续使用和评价
```

四组采用相同任务顺序、模型与总资源规则，状态彼此隔离。每组原成功经验按相同机制更新，不能相互共享另一组产生的失败或成功轨迹。

60道题四组运行，意味着最多240次任务级执行，而不是60次模型请求。成本需要根据实际节点结构估算。

### 冷启动与预载经验必须分开

**主轨：失败算子库空库启动。** 用于检验你设想的自然积累过程。

**辅助轨：预载历史见证。** 用于检验已有少量失败经验时，能否在新任务中产生收益。

后者有助于在失败稀疏时验证机制，但不能混入前者，声称系统从零在线发现了这些经验。

# 六、这轮最关键的实验边界

## 1. 历史回放只能证明积累过程，不能直接证明策略收益

E3-S0原来的8条流彼此独立，合并曲线只是展示；不能把它当作历史上存在一个共享经验库。E3-S0报告

下一步若要模拟一个共享库，需要预先定义新的任务级顺序，并称为**新的模拟流**。

同样，历史中的失败修复发生在后面，就只能在那个时刻之后成为经验。模拟器不能提前读取它。

## 2. 最终隐藏评分不能驱动在线学习

除了隐藏答案和反例，**隐藏PASS/FAIL本身也是信息**。

如果用这个信号决定是否再修复、是否编译、是否入库，它就已经进入在线决策。

建议把在线可用反馈限定为公开测试或预先允许的独立验证；最终隐藏评分只用于外部评价。独立门控另使用封存分片，不能偷用当前任务的最终测试。

若原FlowEvo执行路径依赖最终测试反馈，则应对所有组建立相同的公开反馈适配基线，明确记录协议变化。

## 3. 不能把“低频”与“条件性无效”混在一起

最后至少分别报告三个数：

**未来触发频率、触发后的条件性收益、检测与构建总成本。**

可能出现：

> 算子在触发时明显有效，但自然任务中几乎用不到。

也可能出现：

> 算子经常触发，但Generic同样有效。

它们是不同的研究边界，不能只用一个总正确率解释。
