# FlowEvo v2 S1.1：实现与原设计一致性审查

我对照了《FlowEvo v2 S1.1本地实现与验收》和之前的《失败证据驱动算子：机制修订与下一步实验计划》。

总体判断：核心架构与设计基本一致，但目前实现的是“失败学习系统的基础框架”，还不是完整的在线失败驱动Operator学习系统。

特别是，你最关心的三个功能：

1. 在线不断积累失败经验；
2. 从失败经验自动生成可执行Operator；
3. 验证Operator后让它帮助后续任务；

目前分别处于基本实现、接口已实现但主流程未打通、受控执行已实现但实际收益未验证的状态。

这并不意味着S1.1失败。因为原计划中，S1.1本来就主要负责最小实现与透明性验收，真实生成和实验属于下一阶段。

FlowEvo_失败证据驱动算子_机制修订与下一步实验计划.md

## 二、目前有三个关键差距

### 1. 最核心的“自动生成Operator”尚未完成

原设计要求：

累积可信失败证据

结构化机制规格

生成3个可执行候选

设计集筛选、独立门控及回归

允许后续任务使用

但S1.1报告明确说：

- `BoundedCompiler`目前主要是有预算的宿主回调接口。
- `LearningLoop`自动调度仅到规格归纳。
- 候选生成、修订、设计集选优及独立门控仍需要显式执行。
- 真实API后端尚未配置或调用。

  FlowEvo_v2_S1.1实现与验收.md



因此，现阶段不能称为已经实现自动Operator生成闭环。

这应该是下一阶段优先补齐的功能，而不是继续开发更多错误检测器或增加事件类别。

### 2. 第一版Operator的执行能力比原设计更窄

原设计允许算子内部包含模型调用、参数化工具、确定性计算及多步骤工作流。

粘贴的文本 (1).txt



但目前v2第一版只允许Operator：

- 返回新的代码候选；
- 或者选择公开候选账本中已存在的程序。

暂时不允许算子在自身内部发起模型调用。

FlowEvo_v2_S1.1实现与验收.md



这个限制在S1.1阶段是合理的，因为它简化了预算、权限和回退控制。

不过，后续如果希望自动生成“遇到某类失败时，调用模型进行定向修复”的Operator，就必须增加由宿主控制的模型调用能力。

我建议先不要立即放宽这个限制。 首先验证无需内部模型调用的可执行Operator能否生成、通过独立门控并产生增量价值。

如果研究结果表明需要新模型调用，再通过独立能力代理扩展，不要让算子直接持有API密钥。

### 3. 还没有实际证明新模块在服务器真实FlowEvo中保持原有行为

报告通过了：

- Python 3.9和3.11共93项测试；
- 48题固定历史响应回放；
- 1,112个冻结制品哈希检查。

  FlowEvo_v2_S1.1实现与验收.md



这是有价值的工程证据。

但报告同时指出，服务器实际的 `CodeSkillLibrary`、模型、配置、提取器及平台仍需核实，Linux真实Worker也尚未在目标服务器完成本轮验收。

FlowEvo_v2_S1.1实现与验收.md



所以目前证明的是本地固定响应条件下的兼容性，不是已经证明真实API环境中插件启停完全透明。

## 三、还有四个需要重点核对的设计细节

这些不一定是Bug，但会影响后续实验能否正确归因。

### 1. 单见证启动与三题认证是否真正分开？

原设计的重要修订是：一条可信失败可以触发候选生成，但不能直接获得正式部署资格。

FlowEvo_失败证据驱动算子_机制修订与下一步实验计划.md



当前实现保留了旧 `MechanismStore` 的三题、两来源组认证要求，同时让新的编译队列独立于它运行。

FlowEvo_v2_S1.1实现与验收.md



这是符合设计的。

但实际需要核验：一条可信失败能否真正走到Shadow候选生成，而不是在生成前又被旧认证门槛挡住。

当前单元测试覆盖了单见证触发，但真实生成尚未执行，因此这条端到端链路仍待验证。

### 2. 成功经验库必须在所有实验组中保持公平

当前 `native_adapter.py` 保留历史Prompt和成功经验库接口，并按可信公开测试通过更新成功经验。

FlowEvo_v2_S1.1实现与验收.md



这与原设计要求的“保留成功技能机制”一致。

但是原历史实验与新系统的反馈来源已经发生变化：过去存在使用完整测试反馈的情况，现在建立了共同公开反馈适配基线。

FlowEvo_v2_S1.1实现与验收.md



因此后续比较必须是：

采用同一公开反馈协议的 FlowEvo 原生基线 vs FlowEvo + Failure Operator。

不能把使用旧反馈协议的历史FlowEvo直接作为新系统的严格因果对照。

### 3. 当前候选准入过于保守，但暂时合理

S1.1要求新算子提出的代码候选通过非空可信公开测试，才允许改变当前程序选择。

仅通过语法检查，不足以替换原候选。

FlowEvo_v2_S1.1实现与验收.md



这个要求有利于控制负迁移。

但对于“输出预算耗尽、最后代码不完整”的场景，有时确实不存在可立即获得的高质量公开测试。

这会造成部分Operator即使生成了完整程序，也无法获得应用资格。

建议下一阶段先记录三种情况：有公开测试并通过、有公开测试但未通过、缺少可靠公开测试。不要因为无法满足门槛就静默丢弃候选。

不过当前不建议直接允许结构通过便部署，否则会引入新的误伤风险。

### 4. Active缺失不应该阻止下一步实验

原设计的最终目标包含正式发布的Active算子。

FlowEvo_失败证据驱动算子_机制修订与下一步实验计划.md



但S1.1有意只允许Pilot Experimental，不开放Active晋级。

我认为这个阶段划分正确。

因为你现在首先需要证明：

> 从一条真实失败出发，系统能否生成可执行Operator，并在新的程序上产生实际收益？

只有先回答这个问题，再讨论大规模Active部署才有意义。

## 五、下一阶段应该优先完成什么？

我不建议现在继续扩大失败样本审查，也不建议直接开始60题正式在线流。

下一步应当专门完成 E3-S1.2：真实Operator生成闭环验收。

建议依次完成：

1\. 目标服务器验收。 冻结实际FlowEvo入口、模型、成功库、沙箱及公开反馈协议；核验插件关闭和Shadow模式不会改变原工作流。

2\. 真正打通生成器。 使用已经验证的真实失败作为输入，让系统自动形成规格、生成候选代码、完成设计集筛选。不能只使用人工编写的Operator夹具代替真实生成。

3\. 完成独立门控与回归。 在来源案例之外，检查正例、反例和不适用边界。允许候选最终保持Shadow，不强制产生晋级算子。

4\. 验证受控执行。 只有获得Experimental权限的候选才进入新的独立检查点；保留原生FlowEvo回退与完整费用记录。

5\. 开展B/G/M/F比较。 先评估条件性恢复能力，再决定是否启动真正的在线积累实验。

尤其要保留原设计要求的四组对照：

| 条件               | 作用            |
| ---------------- | ------------- |
| B：原生FlowEvo      | 判断算子整体增益      |
| G：Generic恢复      | 排除普通规则已经足够的情况 |
| M：历史失败文本经验       | 判断是否只需文本记忆    |
| F：生成的可执行Operator | 评价可执行化是否带来增量  |

如果F只优于B，而不优于G或M，仍不足以证明失败驱动Operator机制具有独立创新价值。

## 六、最终判断

| 层面                | 判断              |
| ----------------- | --------------- |
| 与原设计的总体架构         | 基本一致            |
| E3-S1.1工程目标       | 已按报告完成离线验收      |
| 在线失败积累机制          | 已有实现，尚未真实验证长期行为 |
| 自动可执行Operator生成   | 尚未完整实现          |
| Operator可信晋级与正式发布 | 部分实现，Active尚未开放 |
| 在线学习是否改善FlowEvo   | 尚无实验结果          |

因此，现在的问题不是系统设计方向错误，而是最核心的自动生成与验证闭环还没有真正运行。

我建议保持现有v2架构，不再增加新的抽象模块，优先把下面这条链路端到端跑通：

真实失败 → 自动规格 → 生成实际Operator代码 → 独立验证 → Experimental试用 → 后续任务测量收益。

这一步成功，才说明当前系统从“失败证据与路由框架”进化成了真正的失败驱动在线Operator学习系统。
