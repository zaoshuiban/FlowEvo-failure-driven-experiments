# B v11 跨失败机制恢复技能学习设计

本轮检验同一种表示、学习流程、条件检查和沙箱执行能否覆盖两类局部失败。目标是由模型自行从公开轨迹归纳候选，候选能在来源失败后产生可核查的修复，并能在不适用状态拒绝。研究者的两个分层仅用于开发评估和汇报。

| 阶段 | 冻结操作 | 合法失败 |
|---|---|---|
| 逐条分析 | 16 条 B 组轨迹按原序分为两批，每条可归纳或弃权 | 缺失、拒收、弃权 |
| 机制归纳 | 一次调用，根据模型分析及公开引用分组，允许多个机制及单例 | 不归纳、冲突归属、只发现一个机制 |
| 候选生成 | 按已有排序，依来源数、恢复引用数及原顺序最多选两项，在验证之前确定 | 格式不合法、弃权、表示不支持、静态拒绝 |
| 来源验证 | 对每份候选声称支持的全部来源，从实际失败反馈之后开始，在 18 步及原环境剩余步数内执行 | 过度拒绝、合法无进展、反复动作、执行异常 |
| 边界验证 | 每份候选在同一组 14 条开发控制上检查，Worker 返回动作即视为介入，合成环境不执行动作 | 错误介入、信息不足下介入 |

局部见证采用同一评分方法。历史上的第一个得分增长或获胜动作在锚点不可用，候选执行后该确切动作进入合法集合，记作公开障碍解除。分支实际产生得分增长或获胜也单独可核查。环境获胜独立计数。若决定性动作在锚点已经可用，另计为原生路径已可继续，拒绝介入不纳入过度拒绝。第 120 条台灯来源属于这类情况。来源训练同源，仍是开发证据。

若容器和灯具两类各有一份纯来源分层候选完成局部验证，才记跨机制来源见证。混合分层候选保留全部结果，无法独自满足两套技能的条件。局部见证还必须与边界表现分开。候选没有任何局部见证，或出现任一明确或不确定样本介入、执行异常，均不能通过开发筛查。Mock 候选只验证工程表达和执行。

## B v10 失败类型

| 已观察问题 | 分类 | B v11 的通用处理 |
|---|---|---|
| 用多个 selector 合成一个角色 | 表示缺口与不合格式并存。原响应未定义合并语义 | 绑定独立角色，再用关系明确比较，不自动拆解原产物 |
| entities 使用字符串 | 交付格式错误 | 动作及事件参数必须为角色数组，逐条件验证 |
| 轨迹 ID 被用作步骤引用 | 交付格式与证据粒度错误 | 机制归属用轨迹 ID，条件引用用作用域步骤 ID |
| 在 before_failure 检查锚点处失败动作 | 时间和结果语义错误，原条件表达错误 | at_failure 与 before/after 分离，effect 与 noop 分离 |
| 曾拾取被当成仍持有 | 条件本身错误，缺少当前状态证据 | 当前持有角色与历史动作谓词独立，后续状态重新求值 |

原 B v10 的 INVALID_CONDITION 成绩保持原口径。

## Free-Code 对照预留

正式对照使用同样的分析和归并回执、相同两机制排序、来源及边界清单，按冻结条件各生成一份候选。Free-Code 用已有 Python environment_operator、静态检查、实例常量检查和相同 Linux Worker。Structured 用声明条件和动作描述，经宿主检查后进入相同 Worker ABI。两组使用同一模型、非思考、温度 0、每份 4,096 输出上限及相同环境步数。计量共享归纳、每组生成、Worker、回退和交付失败。当前仅冻结 Structured 入口及对照设计，Free-Code 不在此次授权预算内。v5–v10 只能作为背景。

如果真实 Structured 只交付一种有效技能，跨机制假设暂未达到。缺少通用表达能力、学习归纳错误、条件误介入、动作执行失败分开记录。若来源与开发边界均通过，再冻结候选并另设未曝光游戏验证。
