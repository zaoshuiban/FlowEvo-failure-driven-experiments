# ALFWorld B v13 恢复计划编译与验证

B v13 复用 B v12 冻结的三个机制及 23 个已曝光来源检查点。模型提交短恢复计划，宿主编译到现有条件与 Worker 接口。计划及编译结果都在来源回放前绑定到候选版本。这个实验可以分别观察初次编译、静态反馈修订、首动作、局部修复和多步完成。

## 编译和执行

- **角色与引用。** 编译器从失败动作的参数数量建立 `failed_first` 和 `failed_second`。一元动作只有第一个角色。二元动作按位置绑定，也可从同一条公开合法命令提取相关参数。计划只引用已提供的公开步骤 ID，保留全部计划级引用。
- **时间与状态。** `event_is` 要求真实历史回执。`event_recorded` 可以检查完整公开窗口中是否已有匹配回执。当前合法动作和当前对象状态由独立谓词检查。新介入必须对应最新的失败锚点，执行中只允许使用已经出现的公开反馈。停止条件为 `UNKNOWN` 时拒绝执行。
- **执行阶段。** 同一时刻只允许当前阶段选择动作。收到对应动作的有效回执才继续。通用 `repeat_until` 可反复执行当前阶段，直到当前公开条件成立，最多执行 12 次。信息不足、无效果或达到限额时停止。该表示支持有界顺序与条件重复，任意分支及任意循环没有实现。
- **静态反馈。** 每份完整但不合规的提案至多修订一次。修订只收到原始提案、字段级诊断和可用步骤 ID。弃权、供应商截断及发送状态未知分别处理。记录初稿和修订响应哈希及改动字段，字段比较不证明语义等价。Worker、来源回放和独立验证结果不进入修订请求。

## 指标与实验边界

`first_action_executed` 记录实际下发动作，`first_action_verified` 要求公开回执确认对应动作有效。`local_repair_verified` 要求来源的关键动作新变为合法，或 TextWorld 确认得分提升或胜利。`plan_completed` 表示计划阶段均已完成，`won` 仅依据环境胜利回执。到达一个新位置可以满足首动作和计划完成，仍可能没有修复原始任务。

验证使用现有 Docker Linux Worker、TextWorld 和 Shadow Registry。手写夹具只存在于零 API 验收，正式计划生成输入不包含它们。新版本只回放来源及开发边界，所有候选保持 Shadow。

## 零 API 结果

9 项 B v13 测试和 38 项历史回归通过。一次完整 Mock Run 包含三次计划提交、一次静态修订和 62 次真实 Linux Worker 调用。容器夹具的初稿引用了未声明角色，Mock 修订只改动 `steps`，随后成功编译。再次进入同一个 Mock Run 时，模型响应、Worker 回执和预算账本均复用。发送状态未知时停止且未重发。

| 工程夹具 | 首动作有效 | 计划完成 | 局部修复 | 整局获胜 | 明确负例误触发 |
|---|---:|---:|---:|---:|---:|
| 容器，两步顺序执行 | 11/11 | 11/11 | 11/11 | 11/11 | 2/18 |
| 台灯，有界查找后交互 | 3/3 | 3/3 | 3/3 | 3/3 | 1/18 |
| 导航，单步替代移动 | 9/9 | 9/9 | 0/9 | 0/9 | 2/18 |

每份夹具使用相同的 18 条明确负例及 3 条信息不足控制。9 次信息不足测试均拒绝。导航另用合成公开状态验证二元拾取参数从同一合法命令绑定，存在多个匹配位置时拒绝。实际导航来源实验只验证单步移动，未验证由此完成搜索、拾取和投递。三份夹具均有明确误触发，来源成功不构成准入证据。此轮只验证接口表达能力与执行链路，真实模型能否交付并修订计划仍待测。
