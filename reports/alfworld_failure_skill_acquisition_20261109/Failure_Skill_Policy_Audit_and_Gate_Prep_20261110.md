# ALFWorld 冻结策略审查与独立验证准备

## 两个成功策略的行为审查

使用两份 v3 原始源码、原 Registry 版本和冻结 SHA，通过真实 Linux Worker 做 20 次零 API 调用。每个候选检查同样的 6 个合成负例、1 个合成新容器状态和 3 个已曝光来源前缀。合成输入用于暴露决策边界，不能估计真实游戏误触发率。已曝光前缀来自锁定日志，本次只比较第一步的策略输出。

| 检查 | 保险柜 | 微波炉 |
| --- | --- | --- |
| 自己的来源正例 | 1/1 返回正确开启动作 | 1/1 返回正确开启动作 |
| 6 个应拒绝负例 | 3 次误触发，3 次拒绝 | 6 次误触发，0 次拒绝 |
| 非本类目标的两个已曝光容器前缀 | 均拒绝 | 均返回无关的查看动作 |
| 合成新容器闭合状态 | 拒绝 | 返回 `look`，未提出修复 |

**保险柜**存在选择无关容器或误投递的风险。目标是桌面时仍返回 `open safe 2` 或 `move book 1 to safe 2`。题面明确指定 `safe 3`、只有 `safe 2` 可开时，也打开了错误实例。源码会把只在观察中提到、未标明打开的保险柜纳入可能关闭列表，部分回退缺少目标与持有物的核对。

**微波炉**在没有相关证据时会回退到首个符合其过滤条件的合法命令。两个微波炉目标不明确时任取一个；微波炉只用来加热、最终目的地为垃圾桶时，返回把物品放进微波炉。它在其他真实来源前缀上还返回无关查看动作。这些都是候选真实返回值；审查没有继续执行这些动作并测量整局后果。

原 v3 的四个来源获胜仍有效。当前负例结果表明两份候选都需要保留 Shadow。

## B v4 归纳与生成调整

归纳按共同前置条件、预期任务转移、恢复顺序及可观察结果比较证据。首先检查不同容器或物体能否视作同一机制的参数绑定。只有证据支持共同关系才合并；前提、操作或效果不同，或者可见证据不足时，允许分开、保留单例或不分配。

生成要求从公开状态绑定目标物、目标位置和任务阶段。被阻断的命令可以暂时不在合法列表。遇到不确定目标、阶段不符、缺乏证据或没有进展时拒绝，禁止把首个合法动作作为回退。提示词改动已通过零 API 流程检查，实际抽象和拒绝质量仍要由生成产物验证。旧候选源码未修改。

## 独立验证冻结

对已知曝光重新核对了游戏 SHA、轨迹 SHA、任务组和场景。原池 34 局、3 个场景均未运行。目标元数据没有保险柜或微波炉；仅有 5 局橱柜，集中在同一个场景。任务元数据无法判断相关容器在候选决策点是否关闭、物品是否已持有或原生是否会犯错。

已将候选版本、源码哈希、独立池哈希和协议草案绑定。独立运行保持 BLOCKED。草案要求每个主要正负角色至少 4 个独立游戏、覆盖至少 2 个场景，任务组去重。正例分为同类容器新场景和新容器类型两类，负例包含无关容器、错误目标、错误阶段和原生能够成功的状态。按未介入的公开前缀冻结检查点及标签，再从相同检查点比较原生与冻结候选。检查局部修复、整局获胜、拒绝、误触发、原生成功退化及额外动作与请求。标签和覆盖不足时保持阻断。
