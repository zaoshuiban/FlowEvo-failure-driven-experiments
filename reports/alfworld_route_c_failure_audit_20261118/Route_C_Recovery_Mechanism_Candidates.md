# Route C：恢复机制候选与工程替代

日期：2026-11-18。宿主历史开发审查；**没有新增模型归纳或学习技能**。以下“候选”是待研究的问题，不是已经发现并验证的模型算子。所有来源保持曝光开发身份。

## 1. 优先候选：搜索覆盖与子目标状态的恢复

最有增量潜力的方向，是在原生持续无进展、仍有未搜索空间时，恢复已经遗失的公开搜索记忆和对象身份，进行有界探索。它直接关联原生完整失败，不再仅瞄准原生两步就能解决的容器投递问题。

不过，需要拆开三个层次：记录公开事实的状态账本是工程基础；判断何时陷入循环是适用性问题；决定下一步如何脱困才是可学习策略。不能把宿主手写的visited集合当成模型从失败中获得的机制。

| 评价项 | 目前证据 |
| --- | --- |
| 重复性 | 4/17/46三局有较纯粹的搜索覆盖问题；10还混有占手，2混有解析偏差，41混有子目标撤销 |
| 独立性 | 三局不同任务组但同场景6；尚无纯粹搜索失败的跨场景确认 |
| 可观察性 | 已访问地点、内容回执和未访问导航目标来自公开前缀；不需要最终失败或隐藏位置 |
| 可恢复性 | 旧开发探针存在可行路径；简单短扫描并不总能找到目标，部分获胜路线用了后来发现的位置 |
| 可执行性 | 可写有界程序维护已查内容、当前持物、已放对象ID，再从当前合法动作中选择；具体动作选择仍须由学习实验产生 |
| 可验证性 | 可以同状态比较新增发现、合法操作、局部任务前提与剩余预算内整局won；不能只测访问了新位置 |
| 适用边界 | 返回目的地、再次加工、取回错误放置物品可能必要；内容重复不应一律禁用 |
| 增量潜力 | 3局原生未自行恢复，另有2局相关混合失败；可救回数量和成本尚未知 |
| 工程替代 | 持久公开状态摘要、搜索去重、L1→LLM交接摘要、对象ID/完成子目标账本；必须纳入工程对照或共同基线 |

现有 `environment_operator(context)` 接口足以接收公开完整历史、合法动作和有界状态，并返回合法行动或拒绝；并不意味着当前桥接会在这些状态调用它。若未来增加触发器，需要单独冻结其预算、回退和误触发规则。本轮未进行接入。

## 5. 研究优先级

1. 先消除静默解析替换造成的意图/反馈混淆，验证原始动作忠实性，并冻结公平的基础接口。
2. 对搜索记忆和已完成对象维护做明确的工程基线；保留M1/M3作为学习候选，比较模型生成的策略能否超过该基础功能。
3. 增加来自不同场景的自然完整失败，尤其是目标已知但原生仍循环、或长历史后撤销进展的案例；不能依据F收益挑选。
4. 加工流程的短暂错误和已能两步自修复的容器问题放在效率方向，暂不继续扩大容器成功率验证。

目前没有一份Route C候选源码生成或准入。可复用恢复方法的存在是待验证假设，不是本报告已经证明的结论。
