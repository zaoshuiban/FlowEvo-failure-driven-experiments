# 稳定失败驱动的可信算子生成与路由详细设计

> 本设计结合当前 AFlow 项目中的离线算子生成、失败机制归纳、候选锦标赛、算子库和上下文路由实现整理。文中明确区分已有实现与建议完善的部分；参数示例不代表已经获得实验验证的最优配置。

## 1. 研究目标与核心思路

本研究面向智能体工作流在特定任务机制上反复出现的能力缺口，构建一套从失败证据出发，自动生成、验证、管理并调用新算子的闭环方法。

系统的核心过程是：

```text
运行轨迹采集
    ↓
评分审计与失败分类
    ↓
稳定失败机制判定
    ↓
结构化算子规格
    ↓
受约束多候选生成
    ↓
开发集筛选与候选冻结
    ↓
隐藏能力验证与回归检查
    ↓
可信算子库
    ↓
上下文匹配、证据筛选与选择性路由
    ↓
算子执行 / 拒绝与基线回退
    ↓
独立反馈与版本更新
```

三个研究环节分别解决：

1. **生成问题**：如何将重复出现的能力缺口转化为具有明确边界、能够复用的可执行算子。
2. **可信问题**：如何在数据隔离条件下验证算子，并为晋级、更新和淘汰提供证据。
3. **路由问题**：如何判断算子何时适用，使专项能力提升转化为完整工作流的净收益。

“可信”在本设计中表示：算子在指定版本、模型、工具权限、任务范围和预算条件下，获得了独立验证支持。它不表示对任意输入都具有正确性保证。

## 2. 基本对象与系统边界

### 2.1 算子定义

算子是能够在工作流中被独立调用、具有显式输入输出契约、完成一类可复用子任务的能力单元。

算子实现可以包含：

- 专项提示模板；
- 一个或多个模型调用；
- 确定性算法；
- 参数化工具；
- 模型解析与确定性计算的组合。

一个完整算子表示为：

\[
o=(S,P,V,E,L)
\]

其中：

- \(S\)：规格，包括输入、输出、适用条件、拒绝边界和资源约束；
- \(P\)：可执行程序及提示模板；
- \(V\)：版本、代码哈希和依赖指纹；
- \(E\)：开发、隐藏验证、回归和运行证据；
- \(L\)：生命周期状态。

### 2.2 基线定义

需要区分两类基线：

| 基线 | 作用 |
|---|---|
| 原始 AFlow 工作流 | 判断集成后是否改善原系统 |
| 通用两阶段求解器 | 在近似相同调用骨架下评价专项算子增益 |

当前路由实现采用通用两阶段求解器作为默认回退，其过程为“通用分析 → 通用求解”。

实验中应分别报告相对于两类基线的结果。不能把优于通用两阶段求解器直接解释为已经优于原始 AFlow。

### 2.3 离线与在线边界

**离线阶段**负责机制发现、生成、筛选、隐藏验证和算子入库。

**在线阶段**只使用已发布算子及其冻结元数据进行选择、执行和回退。

在线失败可以成为后续离线诊断材料，但不能直接触发未经验证的新代码进入正式路由。

## 3. 数据划分与信息隔离

### 3.1 数据角色

| 数据集 | 用途 | 生成器是否可见 |
|---|---|---|
| 发现集 \(D_{\text{dis}}\) | 发现重复失败、归纳机制 | 可见诊断材料 |
| 设计集 \(D_{\text{des}}\) | 生成、修复与选择候选 | 可见 |
| 隐藏门控集 \(D_{\text{gate}}\) | 冻结候选的独立晋级验证 | 不可见 |
| 回归集 \(D_{\text{reg}}\) | 检查非专项损失与边界行为 | 不可用于生成修复 |
| 最终测试集 \(D_{\text{test}}\) | 评价冻结系统整体效果 | 全流程开发阶段不可见 |

当前离线协议已经区分发现、设计、门控和回归四种角色。最终测试应在此基础上单独保留。

### 3.2 隔离原则

数据隔离至少包括：

1. 规范化题面与题目 ID 不重叠；
2. 同一原题的改写、参数变体和同源实例按组划分；
3. 隐藏题目、答案和逐题反馈不进入生成提示；
4. 路由规则与阈值在最终测试之前冻结；
5. 已用于失败分析的数据不再作为全新隐藏证据。

文本哈希去重只能检查精确或规范化文本重复，不能证明语义独立。参数化问题族还需要记录 `family_id` 或来源组标识。

### 3.3 冻结清单

每次实验创建不可变清单，记录：

```yaml
run_id: ...
dataset_hashes: ...
split_policy: ...
baseline_version: ...
generation_model: ...
execution_model: ...
scorer_version: ...
code_hashes: ...
dependency_versions: ...
random_seeds: ...
timeouts: ...
request_budget: ...
candidate_count: ...
promotion_policy: ...
routing_policy: ...
```

数据、评分器、程序或依赖发生变化后，应创建新版本实验，并明确旧证据是否仍然适用。

## 4. 稳定失败机制识别

### 4.1 原始观察记录

每道题的每次运行保存独立记录：

```json
{
  "problem_id": "...",
  "family_id": "...",
  "run_index": 1,
  "baseline_version": "...",
  "prediction": "...",
  "extracted_answer": "...",
  "score": 0,
  "execution_status": "success",
  "latency_ms": 0,
  "token_usage": 0,
  "scorer_version": "...",
  "trace_path": "..."
}
```

必须保留原始回答，以便评分器修正后离线复评。

### 4.2 失败分类

| 失败类型 | 典型表现 | 处理方式 |
|---|---|---|
| 评分异常 | 答案等价但判错、提取错误 | 修正评分并重评 |
| 基础设施异常 | 网络错误、限流、服务中断 | 单独记录和处理 |
| 执行异常 | 代码报错、超时、空输出 | 分析运行可靠性 |
| 偶发求解错误 | 重复运行大多正确 | 暂不形成机制目标 |
| 稳定机制失败 | 多题、多次出现同类约束违背 | 进入机制归纳 |
| 证据不足 | 无法确认具体错误原因 | 保留为待审计状态 |

基础设施错误不应被计为数学机制错误。若研究对象是正确时间内完成率，则应单独建立包含超时与执行失败的操作性指标。

### 4.3 单题稳定失败

设题目 \(x_i\) 重复运行 \(R\) 次，定义：

\[
e_{ir}=
\begin{cases}
1,&\text{有效执行且答案错误}\\
0,&\text{有效执行且答案正确}
\end{cases}
\]

基础设施异常不进入该机制错误指标，但应完整报告其数量。

题目满足：

\[
\sum_r e_{ir}\ge q
\]

时，可标记为稳定失败题。

当前离线配置默认：

- 每题发现运行 3 次；
- 至少错误 2 次；
- 至少支持 3 道不同稳定失败题；
- 最低经验错误率为 0.20。

这些值用于当前流程的操作性筛选，不构成普遍充分的统计证据。

### 4.4 从稳定失败题到失败机制

同一机制中的题目必须共享可确认的错误结构，例如：

- 对同一类约束发生遗漏；
- 使用了相同的不合法状态转移；
- 在同一类计数问题中重复计数；
- 忽略了同一类定义域条件。

不能仅因为题目都包含“素数”或“括号”就合并为一个机制。

机制记录应包括：

```yaml
mechanism_id: ...
description: ...
violated_constraint: ...
observable_applicability: ...
supporting_problem_ids: [...]
source_fragment_ids: [...]
counterexamples: [...]
excluded_failure_types: [...]
review_status: ...
```

当前机制归纳模块已经支持按观察绑定的原文片段 ID，要求诊断引用对应回答中的实际内容。片段引用有效只证明来源可追溯，机制解释仍需要语义检查。

### 4.5 机制级确认

建议在当前计数门槛上增加：

- 跨参数实例支持；
- 在预先定义的问题族上估计错误率；
- 按题目或来源组计算置信区间；
- 使用近似反例检查机制边界。

同题重复运行存在相关性，不能把所有运行都当作完全独立样本计算置信区间。可采用按题目聚类的自助法估计不确定性。

只有失败样本的诊断包不能用于估计总体错误率。错误率必须来自包含正确与错误观察的完整采样记录。

## 5. 结构化算子规格

### 5.1 规格形式

将失败机制转化为：

\[
S_j=(I,O,P,A,C,R)
\]

其中：

- \(I\)：输入结构；
- \(O\)：输出契约；
- \(P\)：适用前置条件；
- \(A\)：允许的算法骨架；
- \(C\)：复杂度与执行约束；
- \(R\)：拒绝条件。

### 5.2 规格示例

以下为“受限表达式括号化求值”算子的示意规格：

```yaml
operator_id: exact_parenthesization
mechanism_id: incomplete_expression_enumeration

input:
  raw_problem: string
  parsed_fields:
    numbers: list
    operators: list
    preserve_order: boolean

output:
  status: success | declined | error
  response: string
  observation: string
  certificate: optional

preconditions:
  - 数字和运算符能够无歧义解析
  - 输入符合受支持表达式语法
  - 数字数量处于已验证范围

algorithm:
  - 区间动态规划
  - 枚举合法分割点
  - 精确有理数计算
  - 按题目约束处理去重

constraints:
  - 不读取文件或访问网络
  - 对中间状态数量设置上限
  - 对执行时间设置上限
  - 显式处理除零

decline_conditions:
  - 题面解析存在歧义
  - 包含未支持的运算符
  - 参数超出验证范围
  - 预计资源消耗超过预算
```

这份规格必须描述问题族，不能包含只对某一道题有效的答案分支。

### 5.3 规格审查

生成前检查：

1. 适用性是否只依赖当前输入；
2. 输出是否能够被独立评价；
3. 拒绝条件是否可执行；
4. 参数范围是否明确；
5. 算法是否覆盖机制定义；
6. 规格是否混入隐藏数据。

## 6. 受约束多候选生成

### 6.1 生成输入

生成器仅接收：

\[
(S_j,D_{\text{des}},E_{\text{dis}},\mathcal{T})
\]

其中 \(\mathcal{T}\) 为允许的模板或程序语法。

隐藏门控和最终测试材料不得进入生成上下文。

### 6.2 三类生成空间

| 类型 | 可变部分 | 适用场景 |
|---|---|---|
| 固定骨架提示生成 | 专项分析、求解提示 | 主要改善推理策略 |
| 参数化工具生成 | 参数解析、算法配置、工具组合 | 已有通用算法可复用 |
| 受约束程序合成 | 算法主体与局部结构 | 需要新增计算能力 |

当前离线闭环清单标识的生成后端为 `fixed_skeleton_prompt_only_v1`。项目中另有真实代码生成与修复模块，但不能据此认定主闭环已经完成统一的程序合成接入。

### 6.3 候选多样性

每个机制生成 \(K\) 个候选，当前默认 \(K=3\)。

多样性应体现在：

- 算法实现路径；
- 参数解析策略；
- 验证方式；
- 资源控制方式；
- 拒绝边界。

单纯改写提示措辞不一定产生有效的能力多样性。

### 6.4 静态与运行检查

候选首先通过：

1. 语法与接口检查；
2. 导入白名单检查；
3. 禁止文件、网络和进程访问检查；
4. 硬编码题目与答案检查；
5. 超时、内存和状态数量检查；
6. 正常、边界、非法和超范围输入检查。

静态检查不能替代进程级隔离。受约束代码仍应在独立进程中执行，并由外部控制器实施资源限制。

### 6.5 修复边界

候选可以根据设计集反馈进行有限次修复。

修复次数、请求预算和候选数量在运行前固定。隐藏门控失败后，该候选归档；若继续开发，应形成新版本，并使用新的独立门控材料。

API 重试、模型首次生成和源码修复应分别计数，避免把基础设施问题混入生成成功率。

## 7. 候选筛选与可信晋级

### 7.1 逐题配对比较

在相同题目与配置下比较候选 \(o\) 和基线 \(B\)，统计：

- \(W\)：候选正确、基线错误；
- \(L\)：候选错误、基线正确；
- \(T\)：二者同分。

同时记录不同题目的获胜数量，防止同一道题的重复成功撑起全部晋级证据。

### 7.2 开发排序

当前质量函数同时考虑：

- 专项胜负；
- 非专项回归；
- 重复运行稳定性；
- 专项拒绝率；
- 执行错误率；
- Token 开销。

可写为：

\[
Q(o)=
\frac{W-\alpha L}{N_{\text{target}}}
-\beta R_{\text{reg}}
-\gamma(1-S)
-\delta D_{\text{target}}
-\epsilon E
-\zeta\log(1+H)
\]

其中 \(H\) 为正向 Token 相对开销。

质量分用于候选排序；晋级还必须通过独立硬门槛。

### 7.3 当前硬门槛

当前 `PromotionPolicy` 默认要求：

| 指标 | 门槛 |
|---|---:|
| 专项观察数 | 至少 6 |
| 不同专项题数 | 至少 2 |
| 不同获胜题数 | 至少 2 |
| 净胜次数 \(W-L\) | 至少 2 |
| 回归损失率 | 不超过 0.10 |
| 专项拒绝率 | 不超过 0.25 |
| 执行错误率 | 不超过 0.10 |

这些是工程晋级门槛。正式研究还应报告增益置信区间、样本规模及统计不确定性。

### 7.4 隐藏确认流程

```text
设计集比较全部候选
    ↓
选择一个候选
    ↓
冻结代码、提示、范围、依赖及哈希
    ↓
执行隐藏专项验证与独立回归检查
    ↓
全部门槛通过：发布实验版本
任一门槛失败：归档候选
```

隐藏验证不能承担反复选优的职责。否则隐藏集会逐渐变成设计集。

### 7.5 回归评价的双重口径

应分别评价：

1. **算子本体**：直接执行时是否正确、是否恰当拒绝。
2. **完整系统**：拒绝或报错后回退，最终是否正确，付出了多少额外成本。

回归题上拒绝并成功回退，可以视为系统正确，但不能计为专项算子直接解题成功。

## 8. 算子库与证据管理

### 8.1 核心记录

```yaml
operator_id: ...
version: ...
status: experimental

specification:
  mechanism_id: ...
  input_contract: ...
  output_contract: ...
  applicability_rules: [...]
  failure_boundaries: [...]
  parameter_limits: ...

artifact:
  class_sha256: ...
  prompt_sha256: ...
  artifact_sha256: ...
  runtime_dependency_sha256: ...

evidence:
  baseline: ...
  protocol: ...
  dataset_hash: ...
  scorer_version: ...
  execution_model: ...
  target_metrics: ...
  regression_metrics: ...

provenance:
  generation_run_id: ...
  parent_version: ...
  creation_time: ...
```

### 8.2 生命周期

当前库支持：

```text
candidate → experimental / admitted / active
candidate → rejected
experimental / admitted / active → retired
```

当前实现将 `experimental`、`admitted` 和 `active` 都纳入可检索状态，但仍要求证据门控通过。

建议进一步区分实验路由和正式路由的状态策略，使算子生命周期状态与部署环境对应。

### 8.3 证据绑定

证据必须绑定：

\[
(\text{算子版本},\text{制品哈希},\text{范围},\text{基线},\text{协议})
\]

正式完善时，还应绑定执行模型、评分器和关键依赖版本。

代码、提示或依赖改变后，旧证据保留用于历史审计，但不能自动授权新版本调用。

### 8.4 评分器更新

评分器修改后：

1. 使用保存的回答离线重评；
2. 更新失败分组与晋级结论；
3. 使失效的路由证据退出决策；
4. 对受影响算子重新确认资格。

重评结果可以纠正旧结论，但不能被描述为一次新的独立生成实验。

## 9. 上下文感知选择性路由

### 9.1 路由目标

对输入 \(x\)，输出：

\[
g(x)\in\{0,1,\ldots,K\}
\]

其中 \(g(x)=0\) 表示使用基线，\(g(x)=k\) 表示尝试算子 \(o_k\)。

路由不依赖参考答案，也不能假设当前任务的正确性标签已经可用。

### 9.2 输入特征

上下文应逐步覆盖：

| 特征层 | 内容 |
|---|---|
| 任务语义 | 求值、计数、构造、证明等 |
| 结构 | 表达式树、约束关系、代码结构 |
| 参数 | 输入规模、整数范围、状态空间 |
| 边界 | 否定条件、例外、未支持运算 |
| 预算 | 剩余时间、调用次数、Token |
| 证据 | 同范围历史增益、失败与稳定性 |

当前实现主要使用确定性特征与规则。语义解析、参数范围验证和风险校准属于需要继续完善的部分。

### 9.3 路由顺序

```text
提取上下文
    ↓
检查库与元数据
    ↓
排除命中硬失败边界的算子
    ↓
匹配适用规则
    ↓
检查对应版本、范围的有效证据
    ↓
计算排序分数
    ↓
阈值与预算检查
    ↓
选择一个算子，或返回基线
```

硬边界与证据资格必须先于分数比较。较高分数不能覆盖不满足的前置条件。

### 9.4 当前排序公式

当前实现使用：

\[
s_k=\operatorname{clip}_{[0,1]}
\left[
w_k+
0.15\frac{W_k-L_k}{W_k+L_k+2}
+
0.05\min\left(1,\frac{N_k}{20}\right)
\right]
\]

其中：

- \(w_k\)：匹配规则权重；
- \(W_k,L_k\)：当前范围的有效配对胜负；
- \(N_k\)：有效观察数。

默认调用阈值为：

\[
s_k\ge0.70
\]

该分数是启发式排序值，不能解释为“算子正确概率”。

当前证据门槛还默认要求至少 6 次观察、2 道不同题、2 道不同获胜题以及 2 次净胜。

### 9.5 风险与收益联合决策

建议在独立路由开发数据上估计：

\[
U_k(x)=
\widehat{\Delta P}_k(x)
-\lambda_c\widehat C_k(x)
-\lambda_t\widehat T_k(x)
-\lambda_r\widehat R_k(x)
\]

分别表示预期正确率增益、额外成本、额外延迟和误调用风险。

当以下条件同时满足时才调用：

1. 输入位于已验证范围；
2. 当前版本证据有效；
3. 风险低于预设阈值；
4. 收益估计达到最低要求；
5. 执行后仍有足够回退预算。

小样本下优先采用保守规则与范围级证据，避免为每个输入输出缺少校准依据的精确概率。

### 9.6 多算子冲突

多个算子同时匹配时，建议依次比较：

1. 是否满足更精确的前置条件；
2. 证据是否直接覆盖当前子范围；
3. 是否具有更好的收益置信下界；
4. 是否具有更低成本；
5. 是否存在足够选择间隔。

若前两名证据接近且缺乏明确优势，可拒绝专项调用并回退。

当前实现按资格、分数和名称确定性排序，冲突置信度与收益间隔拒绝属于扩展设计。

## 10. 执行、拒绝与回退

### 10.1 统一返回协议

```json
{
  "status": "success",
  "response": "...",
  "observation": "",
  "certificate": null,
  "metrics": {
    "latency_ms": 0,
    "token_usage": 0
  }
}
```

状态含义：

- `success`：完成执行并给出符合契约的结果；
- `declined`：发现不适用，主动拒绝；
- `error`：异常、超时或输出无效。

`success` 表示执行完成，不等于答案已经被证明正确。

### 10.2 二次适用性检查

路由匹配后，算子仍需在解析实际参数后重新检查：

- 语法是否支持；
- 参数是否越界；
- 题目约束是否完整；
- 状态空间是否超过上限。

路由负责粗筛，算子负责执行前精确确认。

### 10.3 回退条件

以下情况进入基线：

- 无符合条件的算子；
- 算子库不可用或元数据无效；
- 制品或依赖哈希不一致；
- 算子主动拒绝；
- 执行异常、空输出或超时；
- 输出违反契约；
- 剩余预算不足。

当前路由已经处理无安全匹配、库异常、制品漂移、拒绝、执行错误与异常回退。统一超时和严格输出契约应由执行控制层进一步保证。

### 10.4 回退成本

完整请求成本为：

\[
C_{\text{system}}
=
C_{\text{route}}
+
C_{\text{specialist}}
+
\mathbf{1}_{\text{fallback}}C_B
\]

因此，采用两调用专项算子后再回退到两调用基线，实际可能产生四次模型调用。

必须报告端到端实际成本和延迟，不能仅用单个算子的调用骨架说明整个系统预算相同。

## 11. 反馈闭环与运行审计

### 11.1 反馈来源

正式能力反馈应来自：

- 有标准答案的离线任务；
- 可独立复核的确定性验证器；
- 明确记录的人工审定结果。

模型对自身结果的自信程度不能直接作为正确性证据。

### 11.2 配对证据要求

只有实际获得候选和基线结果时，才能更新胜、平、负证据。

在线只运行专项算子时，没有观察到基线结果，就不能推断“本次优于基线”。

需要新增配对证据时，可以采用独立离线回放或预先设计的影子评测。

### 11.3 决策日志

每次路由保存：

```yaml
request_id: ...
context_features: ...
library_version: ...
candidate_operators: [...]
blocked_operators: [...]
matched_rules: [...]
evidence_ids: [...]
selected_operator: ...
artifact_hash: ...
execution_status: ...
fallback_reason: ...
total_latency: ...
total_tokens: ...
```

日志应能回答：

- 为什么选择该算子；
- 为什么没有选择其他算子；
- 哪条边界或门槛阻止了调用；
- 是否执行过回退；
- 最终结果与成本如何。

## 12. 实验设计与评价指标

### 12.1 研究假设

**H1：机制驱动生成有效。**  
受稳定失败机制和结构化规格约束的生成方式，在独立专项数据上优于相同预算的通用求解。

**H2：可信晋级有效。**  
隐藏门控与回归约束能够筛除开发表现好、但泛化能力差或副作用明显的候选。

**H3：选择性路由有效。**  
证据与边界约束能够将专项增益转化为混合分布下的系统净收益。

### 12.2 对照组

| 组别 | 用途 |
|---|---|
| 原始 AFlow | 原系统参照 |

理想路由使用答案信息构造实验上界，不属于可部署方法。

### 12.3 测试组成

完整系统测试同时包含：

- 专项题；
- 普通题；
- 近似反例；
- 参数边界题；
- 多算子重叠题；
- 无任何算子适用的题。

专项题富集测试用于测能力边界；自然分布测试用于测实际总体收益。两者应分别报告。

### 12.4 核心指标

| 层次 | 指标 |
|---|---|
| 机制发现 | 有效机制数、证据支持率、机制混淆率 |
| 候选生成 | 可执行率、修复次数、开发成本、候选差异 |
| 可信晋级 | 隐藏增益、不同获胜题数、回归与错误率 |
| 路由 | 专项覆盖率、误触发率、冲突率、拒绝率 |
| 完整系统 | 正确率、正确时间内完成率、净胜率 |
| 成本 | 实际 Token、请求数、延迟分位数、离线生成成本 |
| 可复现性 | 哈希一致率、证据可追溯率、重评一致性 |

定义正确时间内完成指标：

\[
\operatorname{CWT}
=
\frac1N\sum_i
\mathbf{1}
[\text{答案正确且端到端耗时}\le T]
\]

超时、无输出和执行异常均不能计为成功。

### 12.5 消融实验

分别移除：

1. 稳定失败筛选；
2. 结构化规格；
3. 程序空间约束；
4. 多候选选择；
5. 隐藏晋级；
6. 失败边界；

## 14. 端到端算法

```python
def offline_build(protocol, datasets):
    freeze_protocol_and_inputs(protocol, datasets)

    observations = repeat_baseline(datasets.discovery)
    audited = audit_scores_and_failures(observations)

    hypotheses = induce_mechanisms(audited)

    for hypothesis in hypotheses:
        if not passes_stable_failure_gate(hypothesis):
            archive(hypothesis)
            continue

        specification = build_and_review_specification(hypothesis)

        candidates = generate_candidates(
            specification=specification,
            design_data=datasets.design,
            fixed_budget=protocol.generation_budget,
        )

        executable = static_and_runtime_filter(candidates)

        winner = select_on_design_data(executable)
        if winner is None:
            continue

        freeze_candidate_and_scope(winner)

        evidence = evaluate_hidden_and_regression(
            winner,
            datasets.gate,
            datasets.regression,
        )

        if passes_all_promotion_gates(evidence):
            publish_versioned_operator(winner, evidence)
        else:
            archive(winner, evidence)


async def online_solve(problem, budget):
    context = extract_context(problem)

    eligible = retrieve_with_boundary_and_evidence_gates(context)
    selected = choose_under_risk_and_budget(eligible, budget)

    if selected is None:
        return await baseline(problem, budget)

    if not selected.precheck(problem):
        return await baseline(problem, budget)

    result = await execute_with_limits(selected, problem, budget)

    if result.status != "success" or not valid_output(result):
        return await baseline(problem, remaining_budget())

    return result
```

## 15. 预期产出与验收条件

预期形成：

- 可追溯的稳定失败机制档案；
- 统一的算子规格与生成协议；
- 支持受约束生成、修复和候选选择的工具链；
- 带版本、范围、失败边界和独立证据的算子库；
- 支持拒绝、冲突处理与预算回退的路由器；
- 冻结实验协议、原始回答和可重复评价报告。

验收应同时满足：

1. 生成目标具有跨题、跨运行的失败证据；
2. 算子实现具有参数化复用能力；
3. 晋级证据来自生成过程不可见的数据；
4. 路由只调用范围与版本证据有效的算子；
5. 不适用与异常情况能够按预算回退；
6. 完整系统在冻结测试中获得可量化的净收益；
7. 所有结论能够追溯到具体数据、程序、模型与评分版本。
