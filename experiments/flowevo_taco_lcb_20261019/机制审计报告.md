# FlowEvo：312 道最终失败题的评测与工作流机制审计

本次全量链路审计已覆盖 **312 道题、1,560 次原始尝试**，逐份核对代码哈希、原始请求、输出截断、反馈及最后一轮判分。在服务器隔离环境重放所有最终产物：253 份非空程序仍失败，59 份空产物跳过执行。未调用生成模型，未改写原始程序、原始判分或正式成绩。

**这不是 312 份程序均已完成算法正确性证明的报告。** 审计找到了可直接验证的工作流与评测问题，仍有 **163 题**不能可靠细分为“算法选错／状态转移错误／边界错误”。这些未知项完整保留在逐题表中；不能用猜测补齐比例。

## 1. 先看可证实的机制

以下按优先观察到的机制分组，分母为 312 道最终失败题。评测异常表示当前拒绝用例或执行契约存在问题，**不等于该程序在所有有效用例上都正确**。

| 优先观察到的机制 | TACO | LCB | 合计 | 占全部失败题 |
|---|---:|---:|---:|---:|
| 输出预算耗尽，最终产物为空或不完整 | 51 | 10 | 61 | 19.55% |
| 已证实存在比较器、测试数据或评测 I/O 异常 | 76 | 11 | 87 | 27.88% |
| 交互协议与普通 stdin 评测不匹配 | 1 | 0 | 1 | 0.32% |
| 算法根因仍未确定 | 162 | 1 | 163 | 52.24% |
| 合计 | 290 | 22 | 312 | 100% |

“算法根因未确定”中包含 3 道观察到超时的题。超时本身不足以证明选错算法：还要区分渐进复杂度、Python 常数、初始化工作量和执行资源。

### 1.1 输出预算／产物交付：61 题

59 题最后一轮最终文本为空：TACO 50 题、LCB 9 题。另 2 题响应截断后留下未闭合的 Markdown 代码围栏及部分程序，导致语法错误：`taco_0291`、`lcb_atcoder_abc399_e`。61 题最后响应均为 `finish_reason=length`。

它们首先是没有交付可执行完整程序的问题，不能直接贴“算法不会”的标签。这些题的五轮请求合计消耗 **8,515,502 tokens**。工作流在遇到截断后仍沿用相同的 32768 输出上限与 high reasoning 配置；没有专门的预算恢复分支。

### 1.2 TACO：38 道运行错误的解释被明显改变

逐一核对首个失败输入、题面和异常栈后：

- **37 题**存在直接可证实的输入契约违例。完整输入及说明保存在 `runtime_contract_review.json`。
- **1 题 `taco_0382`** 是交互题。模型按交互协议询问，但执行器只有普通 stdin，没有交互器，因此无法正常通信。

几个具体例子：

| 题目 | 实际失败输入的问题 | 原程序表现 |
|---|---|---|
| taco_0038 | n=8，却只给6条边，题面要求7条 | 读取第7条边时越界 |
| taco_0715 | k=7，但数组含8和9，违反 a_i<=k | 差分数组越界 |
| taco_0863 | 规则含 g 至 k，而题面只允许 a 至 f | 六状态数组越界 |
| taco_0911 | n=5，但字符串长6，题面要求8 | 读取后续钥匙/门时越界 |
| taco_0145 | n=274877906945，题面上界10000 | 分配数组时 MemoryError |
| taco_0293 | 整数输入混入 U+0005 控制字符 | int 解析失败 |

这解释了为什么 **IndexError 不必然意味着模型下标算法错误**：若程序按题目保证的范围开数组，测试却违反保证，触发越界不能作为合法输入上的算法反例。这里也没有据此证明这37份程序在所有合法输入上正确。

## 2. “参考解自己也没通过测试器”到底是什么意思

参考解只是数据集中附带的一份程序，不保证它与题面、测试输入和预期输出三者一致。参考解未通过，有至少三种可能：参考程序错、预期输出错，或测试器错。不能单凭“它叫参考解”决定谁对谁错，必须看具体反例。

这次已经有两个可以讲清楚的例子：

### taco_0594：多解题被当成唯一答案

题目要求输出一个排列，使相邻数字乘积不是完全平方数，并明确允许任意合法排列。

数据附带的参考程序输出升序 `1 2 ... n`。这是合法的：相邻正整数互质，若其乘积为平方，则两者都须为平方，而不存在两个相邻的正平方数。对 n=2..500 的独立检查也全部成立。

但数据中的预期输出可能是其他合法排列，例如 n=3 时为 `3 1 2`。本轮模型的倒序 `3 2 1` 同样合法。比较器只比较输出，不能验证这个题目的约束，因此可能拒绝合法参考程序，也可能拒绝合法模型程序。

**这里失败的是“按约束判断答案”的评测契约，而不是已证明模型的构造算法错误。**

### taco_0602：参考距离违反最基本的下界

第一张地图中，S 位于零基坐标 (0,0)，E 位于 (5,9)。每次只能上下左右移动，所以即使没有任何树，至少也需要 5+9=14 步。数据给的预期答案却是11，已经不可能。

独立 BFS 算出的最短路为28步。此前参考 BFS 未通过，不足以证明参考程序错，反而暴露了当前输入和预期输出不相容。

这两个例子的可复算结果在 `reference_explanation_checks.json`。因此，原先199道“答案错误”只能解释为“没有被当前比较器接受”，不能直接解释为199道可信的模型算法失败。

## 3. LCB 错误码：现在已经定位到具体原因

LCB 返回的测试结果码和 TACO 的码表不同。旧适配器混用了同一份文字映射：

| LCB 测试结果码 | LCB 实际含义 | 旧适配器向模型说的 |
|---|---|---|
| -2 | 答案错误（部分函数题也用 False/0） | Runtime or compilation error |
| -3 | 超时 | Runtime error |
| -4 | 运行异常，或编译／测试执行阶段捕获的异常 | Compilation or testing error |

通过判定仍检查“所有用例结果均为1”，所以**文字误译不会直接把失败算成通过**。但修复模型会根据文字判断该修算法、语法还是运行异常，提示错误会影响后续行为。

本次进一步检查了真实请求：**11道失败题的22条修复提示确实包含误译或不准确类别**，其中16条为“Runtime or compilation error”，6条为“Compilation or testing error”。不是只看代码推测有风险。

本次 LCB 最终22道失败的机制分布：

| 机制 | 数量 | 占LCB失败题 |
|---|---:|---:|
| 输出截断／产物不完整 | 10 | 45.45% |
| 合法多解被单一参考文本拒绝 | 5 | 22.73% |
| 浮点精确比较不符合题目精度要求 | 3 | 13.64% |
| 评测器 I/O 模拟不兼容 | 2 | 9.09% |
| 测试参数违反题面契约 | 1 | 4.55% |
| 超时，性能根因尚未进一步证实 | 1 | 4.55% |

### 原先4道 -4 现在不再只有“可能是框架错”

| 题目 | 恢复的异常／原因 |
|---|---|
| abc375_c | MockBuffer.readline 每次返回第一行、不推进读取位置，网格行读取错误后越界 |
| abc314_d | stdout 捕获器为 StringIO，没有 buffer 属性，合法的 sys.stdout.buffer.write 失败 |
| leetcode_3344 | 测试19传入 [0,0]，而题目需要至少三个二维点；解包(x,y)失败 |
| abc399_e | 响应达到长度上限，留下未闭合代码围栏，执行时语法错误 |

所以 -4 是一个执行阶段的大类，不能仅凭它判断“算法错”或“框架错”；现在通过恢复异常元数据，已经能把这4题拆开。

没有让模型重写程序。使用原来的最后一份程序，只将执行方式改成正常 stdin/stdout，并按题意验证构造解或使用1e-9数值容差：

- I/O：abc375_c 36/36、abc314_d 14/14。
- 浮点：abc392_d 42/42、abc385_f 44/44、abc314_e 15/15。
- 多解：abc350_c 3/3、abc311_c 15/15、abc315_e 15/15、abc366_g 29/29、arc181_c 27/27。

此外，leetcode_3344仅剔除不符合点数组契约的测试19后，原程序通过剩余26/26；这也单独保留为诊断对照，未改变原始27例成绩。

这些是诊断对照，不是全新正式benchmark成绩；其余已通过题也未用新判据统一复核，不能据此直接发布“修正后的整体准确率”。诊断代码、全部结果在 `audit/audit_20261020/contract_*` 及 `audit_tools/contract_judge.py`。

## 4. FlowEvo 工作流中可直接看到的失效机制

1. **错误的验证器会驱动错误的修复。** 正确候选可能先被比较器拒绝，模型又收到误译的反馈。此时反复修复不是在解决可靠的算法反例。
2. **修复提示只给粗粒度类别。** 没有实际失败输入、候选输出与预期输出；即便类别正确，也无法区分算法、边界和测试契约错误。
3. **没有针对截断的恢复策略。** 相同配置反复产生空最终文本；两个未闭合代码块又被代码提取器原样返回，进入执行阶段才报语法错误。
4. **只保留上一轮候选，没有保留最优可执行候选。** 33道TACO题早期曾有非空且语法完整代码，最终却为空或语法不完整。这个结论只证明产物退化，不证明早期程序语义正确。
5. **技能检索很弱。** 上游库只存题目前200字符及解答前500字符，以词汇重合检索；修复时可能收到截断且不相关的示例。记录中304/312题有可检索参考，但没有消融实验，不能把304题都归因为检索负迁移。
6. **按当前测试器通过就立即停止。** 因此“已经被该测试器判PASS，随后又被修复改错”的情况是0。注意这不等于“语义本来正确、却因测试器错误被迫修复后改错”的情况也是0；后者尚未完成全量语义证明。

## 6. 数据来源、重放限制与交付物

全部500道TACO、300道LCB的适配题面及测试与服务器缓存下载源逐一核对，无差异；见 `audit/audit_20261020/source_parity.json`。因此，已发现的非法输入和参考值不一致不是本次 prepare_data 的内容改写造成的。下载清单记录固定数据集提交与文件哈希；本审计没有重新在线下载整个数据集。

重放仍使用同一份官方评测源码、隔离环境、原代码与原测试，仅添加诊断记录。`taco_0857` 的错误类别从原始WA变成初始化超时，说明时间敏感结果会受执行环境影响；不拿这次耗时变化推导模型算法优劣。原判分不覆盖。

- `逐题机制审计.csv` / `.json`：312行，含证据等级、机制、说明、最终代码、原响应及诊断轨迹路径。
- `audit_response_hashes.json`：1560份原始响应的哈希。
- `runtime_contract_review.json`：37份运行错误的输入契约证据。
- `contract_findings.json`：专项测试契约核查结果。
- `audit/`：312题全部五轮程序、原始请求与响应、最终判分、完整测试，以及固定版本测试器。
- `audit/audit_20261020/`：312份最终产物重放记录、异常元数据和反事实诊断。
- `audit_tools/`：本地整理、专项契约检查与诊断验证脚本。

优先修复顺序应是：统一LCB错误码与异常元数据；修复I/O模拟；对浮点题、多解题与交互题建立正确的数据契约；隔离或修复非法测试；再在冻结的新评测器上重评所有候选。之后才能对剩余题按算法选择、转移和边界问题做可比较的归因。**本报告没有声称已经完成这163题的算法级归因。**
